# Changelog — standkit / BPMkitStand

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/); версии —
[SemVer](https://semver.org/lang/ru/). Даты — 2026 год.

## [Unreleased]

### Добавлено
- **Кукбук `standkit_hub/web/cookbook.html`.** Standalone-документ в фирменном стиле BPMkit
  (один файл, без CDN и сборки): обзор продукта, установка и ключи запуска,
  разбор дашборда, реестр стендов, виды хостинга (kestrel/iis/docker/k8s),
  удалённые стенды и агент, модель безопасности, траблшутинг, границы
  free/paid и незакрытые заделы. Есть поиск по документу, тёмная и светлая
  тема, кнопки «копировать» на командах. Скриншоты дашборда — настоящие
  (сняты с текущей сборки хаба, встроены в файл; меняются вместе с темой
  документа), а не рисованные схемы. Собран по README, ARCHITECTURE,
  HOSTING, REMOTE_STANDS, SECURITY, ROADMAP, BACKLOG и CHANGELOG.
  Отдельно расписаны: установка **раздельно для Windows и Linux** (в Linux —
  pipx или venv, потому что системный Python закрыт PEP 668), **обновление
  диспетчера** (pip / pipx / venv, что при этом не трогается), три источника
  секретов с приоритетом, и **развёртывание агента-демона на удалённом хосте**
  — раскладка каталогов, где лежит его `projects.json`, токены через
  `STANDKIT_SECRET__…`, systemd-юнит и служба Windows через NSSM.
- **Кнопка «Справка» (?) в шапке дашборда и ссылка в окне «О программе»** —
  открывают кукбук, который отдаётся хабом как `/static/cookbook.html` и входит
  в пакет (package-data `web/*`). Кукбук — обычная статика, а не страница
  приложения: тот же файл открывается с диска, когда диспетчер остановлен.
  Тест `test_cookbook_is_served_as_static_and_self_contained` держит и раздачу,
  и самодостаточность (ни одной внешней ссылки, ни одного обращения к
  `/static/*` изнутри файла).
- **Отдельный диагноз «службы IIS остановлены».** Новый тип
  `IisServiceUnavailableError` и подсказка «поднимите WAS/W3SVC»
  (`sc start WAS` / `iisreset /start`). До живой приёмки IIS 17.08.2026 этот
  случай (код 50, «Служба WAS недоступна») выдавался за нехватку прав, и
  пользователь перезапускал диспетчер от администратора вместо запуска службы.
- **Однократный повтор ЧИТАЮЩЕЙ команды `appcmd` при транзиентном сбое RPC**
  (код 1726 / `hresult:800706be`, код 2147549190 / `hresult:80010006`). Живьём
  такие ответы приходили сразу после операций над пулами, а через секунду та же
  команда работала. Изменяющие команды автоматически НЕ повторяются — к тексту
  ошибки добавляется подсказка про канал управления.
- **Состояние стенда объясняется словами.** У docker- и k8s-бэкендов появился
  `describe_state` (как у IIS): кроме вердикта «жив/не жив» он отдаёт причину,
  которую `check_stand` кладёт в `StandStatus.details['process_reason']` —
  «контейнер приостановлен (docker pause)», «контейнер в цикле перезапуска
  (перезапусков: N)», «деплоймент масштабирован в 0 реплик», «готово 1 из 3
  реплик». Вердикт, вынесенный TCP-фолбэком, помечается `status='unknown'` и
  прямо сообщает, что состояние выяснить не удалось, — «зелёный по порту»
  больше не выглядит как подтверждённый ответ CLI.
- **k8s: `restart` дожидается завершения выката** (`rollout status`,
  `K8S_ROLLOUT_WAIT_SEC`, по умолчанию 60 секунд; `0` возвращает прежнее
  поведение). Раньше вызов возвращался за доли секунды, старые поды были ещё
  готовы, и стенд сразу после «перезапуска» выглядел здоровым, даже если новые
  поды не поднимались.

### Изменено
- **Кукбук переехал из `docs/` в `standkit_hub/web/`** — один файл вместо двух
  копий: он и документ репозитория, и встроенная справка приложения.
  `docs/cookbook.html` удалён, ссылка в README ведёт на новое место.
- **Скриншоты `docs/img/*.png` пересняты** на 0.6.1: в прежних (0.5.x) не было
  ни колонки Redis, ни кнопки «Зарегистрировать стенд».
- **Забрана работа из ветки `docs/cookbook-and-screenshots` (28.07)**, которая
  так и не получила PR: оттуда взяты кнопка «Справка», ссылка в «О программе»,
  правила компактного режима и тест раздачи кукбука. Ветка удалена, чтобы не
  висеть «потерянной работой».
- **Установка в README — с PyPI (`pip install standkit`)**, а не из git. Пакет
  публикуется на PyPI с 0.3.7, но README всё это время предлагал единственный
  способ — установку из репозитория: она ставит незарелизенный `main` и не
  обновляется командой `pip install -U`. Git-вариант остался в README как явный
  «свежий `main` до релиза».
- **`docs/REMOTE_STANDS.md`, установка агента — в выделенный venv** с созданием
  сервисного аккаунта и каталогов, вместо `pip install` из git в текущее
  окружение: агент оформляется службой, а системный Python в свежих
  дистрибутивах закрыт PEP 668.
- **Единый контракт `read_logs`:** при отсутствии CLI все бэкенды возвращают
  `None`. Раньше docker отдавал `None`, а k8s бросал `HostingError`.
- **k8s: логи читаются со всех подов деплоймента** по label-селектору с
  префиксом имени пода. `kubectl logs deployment/X` показывает один под,
  выбранный самим kubectl, — при нескольких репликах часть событий стенда была
  не видна.
- **k8s: `stop` бросает `HostingError`** с текстом kubectl вместо молчаливого
  `False` по ненулевому коду возврата — как `DockerBackend.stop`.

### Исправлено
- **Стенд за HTTPS всегда показывался `http: down`.** Проба `check_stand`
  строила URL жёстко как `http://<host>:<port>`, а `http_ok` шёл в `urlopen`
  с дефолтным SSL-контекстом, проверяющим цепочку сертификатов. Живой стенд
  BPMSoft за TLS с self-signed сертификатом (типовой дев-контур; найдено на
  живой приёмке агента на Ubuntu 18.08.2026) давал `down` при исправных
  `process`/`db` — индикатор врал, оператор видел «стенд лежит» на работающем
  стенде. Появились два поля записи реестра: `stand_scheme` (`http`|`https`,
  по умолчанию `http` — старые реестры не меняют поведения) и `verify_tls`
  (по умолчанию `true`; `false` — не проверять цепочку, для self-signed).
  `http_ok` принимает `verify=` и отключает проверку ТОЛЬКО для `https://`-
  адресов, через публичный `ssl.create_default_context()`. Правка в ядре
  чинит сразу всех потребителей пробы — агент, хаб и локальный путь. Заодно
  ссылка «Открыть стенд» в дашборде строится по той же схеме, а не по `http`.
  Поля НЕ добавлены в форму регистрации дашборда (её белый список полей
  фиксирован в `standkit_hub/server.py` и `web/app.js`) — задавать их пока
  нужно в `projects.json`; см. `docs/BACKLOG.md`.
- **Документация предлагала несуществующую команду задания секрета.**
  `docs/REMOTE_STANDS.md` в трёх местах советовал `python -m standkit.secrets set <ref>`,
  но у модуля нет `__main__`-блока: команда молча завершается с rc=0 и ничего не
  сохраняет, а администратор узнаёт об этом позже — по `401` от агента. Заменено на
  рабочие пути (переменная `STANDKIT_SECRET__<REF>` для службы, `set_secret()` из
  Python для машины с keyring, кнопка «Задать секрет…» в дашборде); в `docs/BACKLOG.md`
  строка про отсутствующий CLI дополнена этим поведением.
- **Внешние утилиты больше не мигают консольным окном** (`appcmd`, `sc`,
  `docker`, `kubectl`, `taskkill`, `tasklist`, `powershell`). У родителя без
  собственной консоли — `pythonw.exe`, служба, фоновый поллер хаба — Windows
  выдавала консоль каждому такому вызову: на экране всплывало и мгновенно
  исчезало чёрное окно. Живьём это выглядело как два мигающих окна раз в
  ~12 секунд (поллер опрашивает IIS-стенд парой `appcmd list site|apppool`).
  Появилась ЕДИНАЯ точка запуска `standkit.platform.run_console` с
  `CREATE_NO_WINDOW` на win32; `hosting._run` (то есть весь путь
  appcmd/docker/kubectl, включая пробы `standkit.adopt`), `sc query`,
  `taskkill`, фолбэк `tasklist` и создание ярлыка через PowerShell переведены
  на неё. Прямой `subprocess.run` в пакете теперь запрещён и стережётся
  тестом `tests/test_no_window.py` (13 тестов, из них два — статическая
  проверка исходников от регресса). Из обычного терминала дефект не
  воспроизводился — дочерний процесс наследовал консоль родителя.
- **IIS: автоопределение сайта заполняет и пул приложений.** `appcmd list apps
  /xml` называет атрибут пула `APPPOOL.NAME`, а код читал `applicationPool` —
  `detect_iis_site` ВСЕГДА возвращал пустой `app_pool`. Следствия: кнопка
  «Определить автоматически» заполняла только сайт, а `kill_worker_processes`
  (требует явного `iis_app_pool`) оставался недоступен для усыновлённого стенда.
  Прежнее имя атрибута оставлено фолбэком. Юнит-тесты этот атрибут не мокали
  вовсе — найдено живой приёмкой IIS 17.08.2026.
- **IIS: `state:Unknown` больше не считается «сайт остановлен».** При
  остановленных службах IIS `appcmd` отдаёт `Unknown` — то есть «сам не знаю».
  Раньше вердикт был `DOWN` с причиной «сайт остановлен (state=Unknown)», то
  есть сломанный канал управления выглядел как штатно погашенный стенд. Теперь
  это неопределённое состояние: вердикт по TCP-порту, а причина прямо называет
  остановленные службы («состояние не выяснено: остановлены службы IIS (WAS,
  W3SVC)»).
- **IIS: ошибка «объект не найден» не выдаётся за нехватку прав.** Список
  признаков elevation был слишком широким (`error ( message:` ловил ЛЮБУЮ
  ошибку appcmd, а код 1168 — это `ERROR_NOT_FOUND`, не отказ в доступе):
  elevated-диспетчер на несуществующем сайте получал совет «запустите от имени
  администратора». Теперь признаки узкие, а «любая ошибка = права» применяется
  только когда процесс действительно НЕ elevated (`IsUserAnAdmin`).
- **IIS: остановка пула больше не падает по таймауту.** `appcmd stop apppool`
  ждёт завершения рабочего процесса, а IIS отводит на это `shutdownTimeLimit`
  (по умолчанию 90 секунд) — общий таймаут внешних команд 20 секунд был мал:
  живьём остановка пула прогретого стенда BPMSoft (.NET Framework) заняла
  20.6 с, диспетчер рапортовал ошибку на штатной операции. У изменяющих
  операций IIS (start/stop/recycle сайта и пула) теперь свой таймаут
  `_IIS_LIFECYCLE_TIMEOUT` = 120 секунд; читающие пробы состояния остались
  быстрыми (дашборд опрашивает их часто).
- **IIS: логи стенда читаются из подпапок-дат.** BPMSoft под .NET Framework
  пишет `Logs\<ГГГГ_ММ_ДД>\Application.log`, в корне каталога `*.log` нет вовсе —
  `read_logs` возвращал `None`, и консоль стенда в диспетчере оставалась пустой
  при живых файлах лога. Плоские логи (kestrel) по-прежнему в приоритете.
- **Остановленный стенд больше не показывается работающим.** Общее правило для
  всех бэкендов хостинга: ответ CLI авторитетнее открытого TCP-порта, фолбэк на
  порт применяется только там, где состояние выяснить не удалось (утилита не
  найдена, команда упала, вывод не разобран). Раньше это правило действовало
  только для IIS; живая приёмка на настоящих Docker и Kubernetes 17.08.2026
  показала два его нарушения:
  - **k8s:** после `stop` (scale 0) `kubectl` честно отвечал «готовых реплик
    нет» — пустой `status.readyReplicas`, — но вердикт перебивался открытым
    NodePort, который слушается всё время, пока существует Service. Стенд
    отображался живым, а сводный статус выходил противоречивым:
    `process=ok, http=down`. Теперь пустой ответ при rc=0 трактуется как
    определённое «не запущен»; нечисловой ответ по-прежнему считается
    неопределённостью и уходит в фолбэк.
  - **docker:** состояние контейнера при `rc=0` теперь окончательное, порт его
    не переопределяет. Заодно вместо `.State.Running` спрашивается
    `.State.Status`: у приостановленного контейнера (`docker pause`)
    `Running=true`, хотя он не обслуживает запросы, — такой стенд показывался
    зелёным.
- **compose-режим больше не путает сервисы с похожими именами.** `is_running`
  сопоставлял имя сервиса как подстроку любой строки `docker compose ps`:
  при поднятом `webhook` неподнятый `web` считался запущенным. Теперь
  используется машиночитаемый `docker compose ps --format json` с точным
  сравнением поля `Service`, а на версиях compose без этого формата —
  табличный вывод с разбором по токенам, а не по подстроке.

### Прочее
- Докстринг `HostKind.K8S` больше не утверждает, что логики k8s ещё нет — она
  есть с 0.5.0 (ADR-0002) и прошла живую приёмку.
- `docs/BACKLOG.md`: раздел приёмки актуализирован, добавлены остатки, найденные
  живым прогоном, и рецепт воспроизводимого k8s-контура на Windows с cgroup v1.

## [0.6.1] — 2026-07-27

### Исправлено
- **Повторный запуск по ярлыку больше не поднимает второй диспетчер.** Ярлык
  стартует хаб через `pythonw.exe`, окна нет, а закрытие браузера процесс не
  останавливает — idle-shutdown у хаба нет. Поэтому второй клик по ярлыку
  запускал ещё один экземпляр: два фоновых поллера дёргали health-пробы и
  внешние команды бэкендов хостинга над одним `projects.json`, а окно
  открывалось на другом origin со своей копией localStorage (сбрасывалась
  тема). На Windows было хуже, чем предполагалось: из-за `SO_REUSEADDR` bind
  на уже слушаемый 8770 проходил успешно, и два хаба молча делили один порт.
  Теперь перед стартом проверяется, не работает ли диспетчер уже — если да,
  просто открывается браузер на нём. Откат на свободный порт сохранён для
  случая, когда 8770 занял чужой сервис.
- **Дашборд честно сообщает, что диспетчер остановлен.** Раньше вкладка с
  умершим хабом продолжала показывать последний снапшот как живой, а
  единственными признаками были красная точка в углу и браузерное
  `Failed to fetch` в тостах. Теперь показывается баннер с объяснением и тем,
  что делать, устаревшая таблица гасится, а сетевые ошибки и 401 («сессия не
  подтверждена» после перезапуска диспетчера) переведены на понятный язык.

## [0.6.0] — 2026-07-27

### Добавлено
- **Усыновление стендов, поднятых вне диспетчера.** Стенд, запущенный руками
  (`dotnet BPMSoft.WebHost.dll` из консоли, скриптом, чужой сессией), теперь
  можно остановить и перезапустить: диспетчер находит владельца порта,
  проверяет, что это действительно процесс ЭТОГО стенда (порт + имя образа из
  allowlist + рабочий каталог внутри `stand_dir`), и берёт его под управление —
  **только с явного подтверждения**. Без подтверждения процесс не трогается.
  В таблице стендов появился бейдж «вне диспетчера».
- **IIS: автоопределение сайта** по physical path и биндингу для стенда,
  развёрнутого мимо диспетчера; снятие зависшего `w3wp` по pid; различение
  состояний «сайт остановлен» / «пул остановлен» / «порт держит http.sys».
- **PWA.** `manifest.webmanifest` + иконки: Chrome и Edge предлагают
  «Установить приложение» — дашборд получает отдельное окно без адресной
  строки, свою иконку в панели задач и место в Alt+Tab. Зависимостей не
  добавилось.
- **Компактный режим** `?view=compact` — узкое окно-виджет: имена стендов,
  состояния и старт/стоп. Доступен ярлыком из установленного PWA.
- `GET /api/stands?probe=0` — слепок реестра без сетевых проб, и
  `GET /api/events` — SSE-поток обновлений состояния.

### Изменено
- **Дашборд открывается мгновенно.** Раньше первый экран ждал полного обхода
  всех стендов: пробы шли последовательно, до 9 секунд на стенд, а конфиг и
  реестр перечитывались с диска на каждый запрос. Три недоступных стенда за
  firewall давали около 27 секунд серого экрана. Теперь состояние собирает
  фоновый поток, а страница рисуется сразу и обновляется по мере готовности.
- **Фиксированный порт по умолчанию — 8770** (с откатом на свободный, если
  занят). Побочный эффект прежнего эфемерного порта: браузер каждый запуск
  считал дашборд новым сайтом, из-за чего сбрасывалась выбранная тема и
  заново качалась статика.
- Тема хранится в конфиге хаба и применяется до загрузки скриптов — тёмная
  больше не мигает светлой при открытии.
- Настройка «интервал автообновления» наконец работает: раньше значение из
  формы ни на что не влияло, интервал был жёстко зашит.
- **Форма настроек разгружена**: сразу видны четыре основных поля, параметры
  федерации и демона-агента убраны под спойлеры, причём блок агента скрыт
  целиком, пока в реестре нет удалённых стендов. У полей появились пояснения
  и подсказки со значениями по умолчанию.
- Остановка стенда стала мягкой: сначала штатное завершение с ожиданием и
  только потом принудительное — стенд успевает закрыть соединения с БД и
  Redis. Раньше на Windows сразу шёл `taskkill /T /F`.
- Статика отдаётся с валидаторами кэша (`ETag`, `304`).

## [0.5.2] — 2026-07-25

### Изменено
- **IIS: жизненный цикл по Site.** Стоп/рестарт/детект работают по **Site**
  стенда; **App Pool не трогаем** (может быть общим с другими приложениями).
  App Pool задействуется только когда `iis_site` не задан. Детект «жив» — по
  состоянию сайта; открытый TCP-порт больше не маскирует остановленный сайт
  (http.sys держит порт). См. [ADR-0004](adr/0004-iis-site-scoped-lifecycle.md).
- **Читаемые ошибки внешних команд.** Вывод `appcmd`/`docker`/`kubectl`
  декодируется utf-8 → OEM (cp866) → cp1251 — больше не «кракозябры».
- **Хаб — тяжёлые логи IIS.** Панель «Текущее состояние» берёт логи только за
  сегодня и читает лишь хвост файла (до 4 МБ) — дневной IIS-лог в сотни МБ не
  грузится целиком.
- Упаковка: SPDX-выражение лицензии (`license = "MIT"`, `license-files`) —
  убран deprecation-warning setuptools.

### Добавлено
- Подсказка «запустите диспетчер от имени администратора» при ошибках `appcmd`
  из-за нехватки прав (IIS требует elevation).
- Кнопка «Обновить» даёт обратную связь (блокировка + «Обновление…» + время).
- Колонка **Redis** в таблице стендов с номером базы.
- Обратная связь и надёжность первого запуска: папка реестра создаётся при старте
  диспетчера и при первой записи.

### Исправлено
- **Честный отказ** при остановке стенда, запущенного вне диспетчера (нет
  pidfile): вместо мнимого «остановлено» — понятная ошибка.
- Логи стенда ищутся в подпапках по датам (рекурсивный листинг) — раньше хаб
  ошибочно сообщал «в каталоге нет файлов».
- Модалки не закрываются при выделении текста мышью с отпусканием за краем окна.
- Колонки таблицы не «прыгают» при смене статуса; HTTP-значение — кликабельная
  ссылка; кнопки в модалках не слипаются.
- `Ctrl+C` завершает `standkit-hub` чисто, без трейсбека `KeyboardInterrupt`.
- Дедуп SVG-ассетов; TODO-докстринги урезаны до ссылок на документацию/бэклог.
