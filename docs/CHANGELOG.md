## [Unreleased]

### Добавлено

- **Канал релизов заранее узнаёт о занятом файле, а не только по факту неудачной
  подмены (GAP-161).** До этого `apply_staged` выяснял, что MCP-сервер держит
  бинарь, единственным способом — `PermissionError` из `replace_with_retry`,
  уже ПОСЛЕ того, как сделан бэкап. Теперь ДО бэкапа и до любой мутации идут две
  проверки подряд:
  - `standkit_companion/mcp_mutex.py` (новый модуль) — на Windows проверяет
    существование именованного системного мьютекса `BPMkitMcpServer`, которым
    MCP-сервер сам объявляет о своей работе (`SERVER_MUTEX_NAME`/
    `acquire_server_mutex()` в `bpmkit/core.py` поставки BPMkit, GAP-155б;
    имя продублировано константой с явным комментарием-контрактом — импорт
    между отдельными репозиториями невозможен). Найден — отказ с отдельным,
    отличимым от прочих кодом `kind="mcp_running"`. Любая ошибка WinAPI
    подавляется (fail-open ДЕТЕКТА): не смогли определить — работаем как
    раньше, финальную защиту даёт следующий шаг и сама подмена. На не-Windows —
    тихий no-op, поведение не меняется;
  - `fsutil.probe_writable()` (новая функция) — неразрушающая попытка открыть
    целевой бинарь на запись (`r+b`, без усечения) прямо перед бэкапом. Ловит
    занятый файл ЛЮБОЙ природы (старый сервер без мьютекса, посторонний
    процесс), отказывает тем же текстом, каким закончилась бы настоящая
    подмена, но раньше — до того, как сделан бэкап (`kind="local_io"`).

  Обе проверки дополняют, а не заменяют обработку `OSError` из
  `replace_with_retry` — она остаётся последней линией защиты. Установленная
  версия и подготовленное обновление не трогаются ни в одном из новых путей
  отказа.

### Безопасность

- **Канал обновлений больше не ходит по открытому `http://` (fail-closed
  политика транспорта).** Издатель переехал на домен с валидным сертификатом,
  и транспорт канала с этого выпуска ОТКАЗЫВАЕТСЯ работать по незащищённому
  адресу: `BackendClient` проверяет схему `base_url` в конструкторе — до того,
  как уйдёт хоть один запрос, — и на не-`https` адрес поднимает
  `ChannelError(kind="insecure_transport")` (новый вид ошибки: не retriable,
  показывается пользователю). Причина та же, по которой fail-closed вся политика
  подписи: по каналу едет исполняемый файл MCP, по открытому соединению его
  можно подменить по дороге, а лицензионный конверт уезжает открытым текстом в
  заголовке `Authorization`. Отвергается не только явный внешний `http://`, но и
  адрес без схемы (`updates.example`), и любая другая схема: «неизвестно,
  защищено ли» fail-closed читает как «не защищено».
  - **Исключение ровно одно — loopback** (`localhost`, `127.0.0.0/8`, `::1`):
    именно так поднимается настоящий бэкенд рядом — в интеграционных тестах
    транспорта и в живой приёмке канала, — и такой трафик не покидает машину.
    Хост разбирается через `ipaddress`, а не сравнением строк: имя
    `127.0.0.1.evil.test` — чужой хост, а не loopback.
  - **Аварийный выход для отладки — именованный `BackendClient(...,
    allow_insecure=True)`**, и только он. Переменной окружения, снимающей запрет,
    нет намеренно: обход обязан быть виден в коде вызывающего, а не в чужом
    окружении (тот же принцип, что у `--insecure` в `standkit_agent`). Отдельный
    тест сторожит, что такая переменная не появится «для удобства».
  - **Downgrade на редиректе** (`https` → `http`) закрыт прежней проверкой
    «редирект только внутрь `base_url`»: схема входит в префикс адреса, поэтому
    второй, параллельной политики не заводилось — две проверки про одно и то же
    однажды разъехались бы молча. Заодно у этой проверки появилась ГРАНИЦА
    префикса: `https://api.example` больше не считается своим адресом для
    `https://api.example.evil.test/`, который раньше проходил как свой.

## [0.9.0] — 2026-08-20

> ✅ **Обратно совместимо, действий не требуется.** Старые `standkit-hub.json`
> читаются как есть: секция `companion` отсутствует — `CompanionSettings.from_dict`
> достраивает её дефолтами. Свободная редакция (без пакета `standkit_companion`)
> ведёт себя ровно как раньше: новая вкладка честно сообщает, что канал недоступен,
> управление стендами не меняется.

### Добавлено

- **Канал доставки обновлений издателя — пакет `standkit_companion`.** Транспорт
  (и только он): HTTP-клиент к бэкенду издателя, планировщик трёх циклов в ОДНОМ
  фоновом потоке, проверка целостности и подписи, атомарная раскладка файлов,
  откат. Три цикла — три политики, потому что у них разная цена ошибки:
  - **паттерны** (`patterns.py`) — дельта-синхронизация markdown библиотеки
    паттернов с курсором-парой `(since, since_id)`; проверяется **целостность**
    (`sha256` записи + `bundle_sha256` страницы). Файлы — проекция состояния:
    обновления едут в отдельные `dev/patterns_<область>_updates.md` и в
    управляемый блок индекса, поставочные файлы не дописываются никогда. Цикл
    включён по умолчанию, интервал 30 минут (не чаще 5);
  - **релизы MCP** (`releases.py`) — проверка без скачивания файла
    (`HEAD` + `/meta`), стейджинг, применение, откат по истории версий с
    резервными копиями. Политика подписи **fail-closed и без флага отключения**:
    нет сайдкара, `signed: false`, не сошёлся sha256, нет публичного ключа —
    обновление не применяется, прежняя версия не трогается. Цикл **выключен по
    умолчанию** (см. «Известные ограничения» ниже);
  - **отзыв лицензий** (`revocations.py`) — публичный эндпоинт БЕЗ лицензионного
    конверта (отозванная лицензия иначе никогда не узнала бы об отзыве), подпись
    проверяется всегда, документ пишется на диск байт в байт.
- **Проверка подписи Ed25519 на чистом Python** (`standkit_companion/ed25519.py`,
  RFC 8032, PureEdDSA, только `verify`) — инвариант stdlib-only сохранён,
  `cryptography`/`pynacl` не добавлены в зависимости. Строгая проверка `S < L`
  закрывает malleability подписи.
- **Лицензионный контекст запрашивается у CLI самого MCP**
  (`context.py`: `bpmkit setup companion-context --json` через
  `standkit.platform.run_console`). Третьей копии лицензионной логики не
  заводится; «нет CLI рядом» (`ContextUnavailable`) и «нет лицензии»
  (`no_license`) — разные отказы, потому что чинятся по-разному.
- **Точка расширения редакции в хабе.** `standkit_hub/server.py` импортирует
  пакет мягко (`try/except ImportError`); редакция определяется **наличием
  модуля**, а не флагом в конфиге и не именем файла. Отсюда `edition`
  (`"companion"` / `"free"`) и опциональный `companion_version` в `/api/version`.
- **Маршруты хаба `/api/companion/*`:** `GET /status` (выключенный канал — тоже
  `200`: UI обязан показать, почему ничего не происходит) и шесть действий —
  `POST /sync`, `/check-update`, `/stage-update`, `/apply-update`, `/rollback`,
  `/revocations`. `stage-update` и `rollback` принимают `{"version": "..."}`.
  Типизированные отказы канала раскладываются по кодам: `402` — нужна лицензия
  или действие с ней, `503` — рядом нет CLI BPMkit (и он же — ответ свободной
  редакции), `409` — конфликт с текущим состоянием (нечего применять, некуда
  откатываться) или выключенный рубильник, `502` — отказ на стороне
  канала/бэкенда издателя.
- **Вкладка «Обновления» в дашборде** и раздел «Канал обновлений» в настройках:
  состояние трёх циклов, кнопки явных действий, включение циклов и интервалы,
  путь к CLI BPMkit, «Скачивать обновление заранее», строгий режим паттернов.
- **CLI канала — `python -m standkit_companion <команда>`:** `status`
  (плюс `--json`), `sync`, `check-update`, `stage-update [--version]`,
  `apply-update`, `rollback [--version]`, `revocations`, `run [--once]`.
  Три кода возврата с разным смыслом: `0` — сделано, `1` — отказ по существу,
  `2` — ошибка использования или окружения. Стек-трейс наружу не летит никогда.
  Отдельного консольного скрипта в `pyproject.toml` намеренно нет.
- **Новый раздел кукбука «Канал обновлений» (08)** — что приезжает, чем
  различаются три цикла и почему у них разная политика, где лежат файлы,
  почему после установки обновления нужен полный перезапуск Claude Desktop,
  таблица диагностик «сообщение → что произошло → что сделать». Разделы
  «Траблшутинг» и «Границы» сдвинулись на 09 и 10.
- **[ADR-0005](adr/0005-companion-transport-in-mit-core.md)** — «Транспорт канала
  обновлений живёт в MIT-ядре; редакция определяется наличием модуля»: почему
  прежняя формулировка «Companion здесь не живёт» заменена, какие альтернативы
  отвергнуты (приватный репозиторий, `entry points`, флаг редакции в конфиге) и
  закрытый список «чего модуль не делает никогда».
- **`SECURITY.md` §4.2** — разбор новой поверхности: fail-closed подпись
  исполняемого артефакта, публичный ключ из поставки, запрет редиректов за
  пределы базового URL, запись только в пользовательские каталоги, применение
  обновления как явное действие человека, изоляция лицензионного конверта.
  Отдельным блоком — остаточные риски.

### Изменено

- **Новая секция `companion` в конфиге хаба `standkit-hub.json`**
  (`standkit_hub/config.py`: `CompanionSettings`, `CompanionCycle`, поле
  `HubConfig.companion`). Старые конфиги читаются без изменений — отсутствующая
  секция и отсутствующие ключи достраиваются дефолтами. Поля: `enabled`
  (главный рубильник), `backend_url`, `mcp_cli`, три цикла
  `patterns`/`releases`/`revocations` (`enabled` + `interval_sec` с нижней
  границей на каждый цикл), `auto_stage_release`, `require_pattern_signature`.
  Дефолты: паттерны и отзыв включены (30 минут), **релизы выключены** (сутки).
  `PUT /api/settings` сливает присланную секцию поверх текущей, а не заменяет
  её целиком: форма, приславшая один ключ, не должна обнулять остальные.
  Чего в секции НЕТ намеренно: лицензионного конверта и любых токенов
  (в конфиге живут только ссылки на секреты) и флага «не проверять подпись
  бинаря».
- **`HubHTTPServer` поднимает планировщик канала в конструкторе** — до поллера
  стендов и при двух условиях сразу: пакет установлен и `companion.enabled`
  включён. Отказ старта канала НЕ роняет хаб: причина оседает в
  `server.companion_error` и уходит в статус вкладки. `server_close()` гасит
  канал вместе с поллером, до закрытия сокета.
- **`ROADMAP.md` и `BACKLOG.md` приведены к факту.** Строки «Companion — платная
  редакция… здесь не живёт» и «вне этого репозитория» заменены: в репозитории
  живёт транспорт, у издателя — лицензия, содержимое паттернов и подписанные
  бинари. В ROADMAP добавлено состояние канала по циклам, в BACKLOG — раздел
  «Канал обновлений — что ещё не готово». Обоснование смены — ADR-0005.
- **`docs/ARCHITECTURE.md`** — новый раздел про пакет (место в схеме, три цикла
  и почему у них разная политика, где лежит состояние и файлы, взаимодействие с
  хабом и с MCP, рубильник для тестов) и обновлённая таблица разделительной
  линии free/paid: линия проводится по ЦЕННОСТИ, а не по расположению кода.

### Прочее

- **Переменная окружения `STANDKIT_COMPANION_DISABLED`** (`runner.DISABLE_ENV`)
  запрещает старт фонового планировщика канала. Нужна не пользователю, а
  автотестам и CI: цикл паттернов включён по умолчанию, а хаб поднимает
  планировщик в конструкторе — значит на машине с установленной платной
  редакцией и живой лицензией каждый из сотни тестов, поднимающих хаб, заводил
  бы настоящий фоновый поток и при неудачном жребии разброса первого тика
  реально ушёл бы в сеть к бэкенду издателя посреди прогона. Корневой
  `conftest.py` выставляет её на весь прогон через `setdefault` — осознанно
  поднятую разработчиком переменную это не перебивает. Пустая строка и
  `0`/`false`/`no`/`off` считаются «не запрещён».

### Известные ограничения

- **Цикл релизов MCP выключен по умолчанию** (`companion.releases.enabled =
  false`) и включается владельцем явно. Два блокера на стороне издателя: не
  выпущен ключ подписи артефактов и бэкенд обслуживается по `http://` без TLS.
  Пока они открыты, fail-closed политика отвергла бы каждое обновление — цикл не
  тикает вовсе, вместо того чтобы ежедневно отчитываться об отказе.
- **Подписи markdown-паттернов пока нет**, поэтому для них проверяется только
  целостность (`sha256` записи и `bundle_sha256` страницы) — она ловит порчу в
  канале, но не подмену. Строгий режим `require_pattern_signature` существует, но
  включённый сегодня просто остановит цикл: механизма подписи тела у издателя
  ещё не существует.

## [0.8.0] — 2026-08-18

> ⚙️ **Требуется действие оператора.** Ничего не ломается при обновлении, но
> часть улучшений включается полями реестра: `agent_ca` (доверие сертификату
> агента), `logs_dir` (нестандартный каталог логов), `redis_host`/`redis_port`
> (адрес Redis). Все они теперь задаются из формы «Зарегистрировать стенд» —
> править `projects.json` руками не нужно.

### Добавлено

- **Форма «Зарегистрировать стенд» перестала быть уже модели.** В белые списки
  полей (`standkit_hub/web/app.js::_REGISTER_FIELD_NAMES` и
  `standkit_hub/server.py::_REGISTER_ALLOWED_FIELDS`) и в разметку добавлены
  `stand_scheme`, `verify_tls`, `redis_host`, `redis_port`, `logs_dir`,
  `agent_ca`, `agent_verify_tls`. Чекбокс «Проверять сертификат» виден только
  при схеме `https`; поля скрытого условного блока на сервер не уходят вовсе, а
  булев чекбокс отправляется настоящим `true`/`false` — раньше «выключено»
  приезжало как отсутствующее поле и молча давало дефолт `true`
  ([GAP-001](GAPs/GAP-001-registry-fields-out-of-hub-form.md)).
- **Причина отказа HTTP-пробы.** `standkit/health.py` получил `http_probe()` и
  `HttpProbeResult`; распознаются отказ соединения, таймаут, DNS, ошибка
  TLS-рукопожатия, непрошедший проверку сертификат, 5xx и «ответ не по
  протоколу HTTP». Диагноз с фактическим URL кладётся в
  `StandStatus.details["http_reason"]` — по образцу `process_reason` — и
  показывается подсказкой к ячейке HTTP в дашборде (пунктирное подчёркивание =
  причина есть). Для самого частого случая выдаётся рецепт: «похоже, стенд за
  TLS: задайте `stand_scheme=https` (и `verify_tls=false` для self-signed)».
  Автодетект схемы сознательно не делался — разбор в
  [GAP-002](GAPs/GAP-002-http-probe-down-not-explained.md).
- **`redis_host` / `redis_port` — поля модели `Stand`**, а не нетипизированные
  ключи `extra`. Пара валидируется целиком (половина пары — явная ошибка, а не
  молчаливый `unknown`), поля есть в форме и в `projects.sample.json`. В
  дашборде различаются «адрес Redis не задан в реестре» и «Redis не отвечает на
  …» ([GAP-003](GAPs/GAP-003-redis-endpoint-in-extra.md)).
- **`agent_ca` / `agent_verify_tls` — доверие сертификату агента со стороны
  хаба.** `standkit_hub/client.py` строит SSL-контекст явно
  (`ssl.create_default_context(cafile=…)`), снятие проверки действует только
  для `https://`-адресов. Самоподписанный сертификат агента больше не требует
  `SSL_CERT_FILE`, заданной до старта хаба
  ([GAP-008](GAPs/GAP-008-agent-cert-trust-on-hub.md)).
- **`logs_dir`** — явное указание каталога логов стенда в реестре, для
  нестандартной раскладки ([GAP-006](GAPs/GAP-006-log-dir-case-and-separator.md)).
- **Preflight путей у агента.** `standkit_agent` проверяет доступность
  `run_dir`, `log_dir` и файла аудита **до** печати «слушаю …» и до открытия
  сокета. Шаблон `standkit-agent.service` задаёт все три пути явно и объясняет
  комментарием, почему это обязательно для сервисного аккаунта, созданного с
  `--no-create-home` ([GAP-007](GAPs/GAP-007-agent-paths-raw-traceback.md)).
- **[docs/README.md](README.md) — карта документации:** кому какой документ, чем
  различаются ROADMAP / BACKLOG / GAPs и куда заводить новую находку.
- **`docs/COOKBOOK_LINUX.md` — кукбук развёртывания агента на Linux.** Пошагово:
  PEP 668 и установка через pipx / venv в `/opt`, реестр по явному пути,
  секреты в файле окружения, первый запуск, проверка API, служба systemd с
  выделенным сервисным аккаунтом, TLS и mTLS, сетевой периметр, эксплуатация
  (ротация токена, lockout, смена порта контейнера, аудит). Все команды и все
  сообщения об ошибках сняты с живого прогона на Ubuntu 24.04, а не составлены
  по памяти. Отдельные разделы — таблица типичных проблем, клиент на Windows
  (`curl.exe` / `Invoke-RestMethod`) и чек-лист приёмки.
- **Кукбук дополнен разделом «Подключение из дашборда оператора»** по итогам
  живой проверки контура между машинами (дашборд на Windows ↔ агент на Linux):

### Исправлено

- **Каталог логов не находился на Linux.** Имя подкаталога искалось жёсткой
  строкой `"logs"`, а BPMSoft раскладывает логи в `Logs`; на Windows это годами
  прощала регистронезависимая ФС. Резолв вынесен в
  `standkit/logs.py::find_logs_subdir` / `stand_logs_dir`: сравнение по
  `casefold()` через `os.scandir`, точное совпадение регистра в приоритете,
  никакой жёсткой замены `"logs"` → `"Logs"`. Общей функцией пользуются и хаб,
  и `IisBackend.read_logs`. Фиксы Windows/IIS — подпапки-даты,
  `iis_stdout_log_dir`, рекурсивный обход — не тронуты
  ([GAP-006](GAPs/GAP-006-log-dir-case-and-separator.md)).
- **Пути POSIX-стендов больше не показываются с обратными слэшами.** Путь
  удалённого стенда собирался `pathlib.Path` на Windows-хабе, и в сообщение
  уезжало `\mnt\composers\…` — теперь для POSIX-путей используется
  `PurePosixPath`.
- **Для `transport=agent` хаб не врёт «каталог не найден».** Каталог логов
  живёт на файловой системе хоста стенда, локальная проверка о нём ничего не
  знает — сообщение говорит это прямо (`logs_unavailable_reason`).
- **`BadStatusLine` больше не вылетает из HTTP-пробы наружу.** В перехват
  добавлен `http.client.HTTPException`: он не наследуется от `OSError` и мимо
  прежнего `except` проходил насквозь.
- **Агент не падает сырым traceback на служебном запуске.** `PermissionError`
  на каталоге логов/аудита, отсутствующий `$HOME` у сервисного аккаунта и
  занятый порт превращаются в одну понятную строку с путём, пользователем и
  нужным флагом, код возврата `1`. Строка «слушаю …» больше не печатается
  раньше фактического старта
  ([GAP-007](GAPs/GAP-007-agent-paths-raw-traceback.md)).
- **`CERTIFICATE_VERIFY_FAILED` больше не показывается как «агент недоступен».**
  Различаются недоверенный CA, несовпадение имени с CN/SAN сертификата и
  ненайденный файл `agent_ca` — у каждого свой рецепт
  ([GAP-008](GAPs/GAP-008-agent-cert-trust-on-hub.md)).
- **«слушаю …» печатается после фактической привязки сокета.** `run_server`
  получил колбэк `on_ready`, который зовётся после bind/listen (и после
  `wrap_socket` при TLS). Раньше на занятом порту оператор видел «слушаю …»,
  а следом отказ — журнал читался как «стартовал и сразу упал».
- **Каталог логов находится и там, где нет права листинга.** Резолв сначала
  пробует прямой путь (достаточно права прохода `--x`, как было до 0.8.0) и
  только потом идёт в `os.scandir` за регистронезависимым поиском: каталог
  стенда с правами `0711` перестал давать ложное «каталог не найден».
  Отсутствие прав отличается от отсутствия каталога и в тексте сообщения.
- **Путь Windows-стенда на Linux-хабе** больше не собирается в смесь
  разделителей (`C:\BPMSoft\stand/logs`) — зеркальный случай к фиксу выше.
- **IPv6-адрес в тексте причины HTTP-пробы** сохраняет скобки: URL из подсказки
  снова можно скопировать в браузер.
- **Windows: агент больше не занимает уже слушаемый порт.** У
  `ThreadingHTTPServer` включён `SO_REUSEADDR`, и на Windows это разрешает
  второму процессу занять УЖЕ слушаемый порт — bind проходит, `EADDRINUSE` не
  возникает, два агента оказываются на одном порту, а входящие соединения
  распределяются между ними непредсказуемо. Для агента, который по этому порту
  запускает и останавливает процессы, тихое раздвоение недопустимо. Перед
  bind'ом на Windows выполняется проба «кто-то уже слушает?», и занятый порт
  даёт тот же понятный отказ, что и на Linux. `SO_REUSEADDR` при этом не
  отключается — иначе на Windows ломался бы быстрый перезапуск службы
  (соединения в TIME_WAIT). Та же грабля для дашборда была разобрана раньше,
  см. `standkit_hub.server.probe_hub_instance`.

### Исправлено
- **Стенд за HTTPS всегда показывался `http: down`.** Проба `check_stand`
  строила URL жёстко как `http://<host>:<port>`, а `http_ok` шёл в `urlopen`
  с дефолтным SSL-контекстом, проверяющим цепочку сертификатов. Живой стенд
  BPMSoft за TLS с self-signed сертификатом (типовой дев-контур; найдено на
  живой приёмке агента на Ubuntu 18.08.2026) давал `down` при исправных
  `process`/`db` — индикатор врал, оператор видел «стенд лежит» на работающем
  стенде. Появились два поля записи реестра: `stand_scheme` (`http`|`https`,
  по умолчанию `http` — старые реестры не меняют поведения) и `verify_tls`
  (по умолчанию `true`; `false` — не проверять цепочку, для self-signed).
  `http_ok` принимает `verify=` и отключает проверку ТОЛЬКО для `https://`-
  адресов, через публичный `ssl.create_default_context()`. Правка в ядре
  чинит сразу всех потребителей пробы — агент, хаб и локальный путь. Заодно
  ссылка «Открыть стенд» в дашборде строится по той же схеме, а не по `http`.
  Поля НЕ добавлены в форму регистрации дашборда (её белый список полей
  фиксирован в `standkit_hub/server.py` и `web/app.js`) — задавать их пока
  нужно в `projects.json`; см. `docs/BACKLOG.md`.
- **Документация предлагала несуществующую команду задания секрета.**
  `docs/REMOTE_STANDS.md` в трёх местах советовал `python -m standkit.secrets set <ref>`,
  но у модуля нет `__main__`-блока: команда молча завершается с rc=0 и ничего не
  сохраняет, а администратор узнаёт об этом позже — по `401` от агента. Заменено на
  рабочие пути (переменная `STANDKIT_SECRET__<REF>` для службы, `set_secret()` из
  Python для машины с keyring, кнопка «Задать секрет…» в дашборде); в `docs/BACKLOG.md`
  строка про отсутствующий CLI дополнена этим поведением.
- **Внешние утилиты больше не мигают консольным окном** (`appcmd`, `sc`,
  `docker`, `kubectl`, `taskkill`, `tasklist`, `powershell`). У родителя без
  собственной консоли — `pythonw.exe`, служба, фоновый поллер хаба — Windows
  выдавала консоль каждому такому вызову: на экране всплывало и мгновенно
  исчезало чёрное окно. Живьём это выглядело как два мигающих окна раз в
  ~12 секунд (поллер опрашивает IIS-стенд парой `appcmd list site|apppool`).
  Появилась ЕДИНАЯ точка запуска `standkit.platform.run_console` с
  `CREATE_NO_WINDOW` на win32; `hosting._run` (то есть весь путь
  appcmd/docker/kubectl, включая пробы `standkit.adopt`), `sc query`,
  `taskkill`, фолбэк `tasklist` и создание ярлыка через PowerShell переведены
  на неё. Прямой `subprocess.run` в пакете теперь запрещён и стережётся
  тестом `tests/test_no_window.py` (13 тестов, из них два — статическая
  проверка исходников от регресса). Из обычного терминала дефект не
  воспроизводился — дочерний процесс наследовал консоль родителя.
- **IIS: автоопределение сайта заполняет и пул приложений.** `appcmd list apps
  /xml` называет атрибут пула `APPPOOL.NAME`, а код читал `applicationPool` —
  `detect_iis_site` ВСЕГДА возвращал пустой `app_pool`. Следствия: кнопка
  «Определить автоматически» заполняла только сайт, а `kill_worker_processes`
  (требует явного `iis_app_pool`) оставался недоступен для усыновлённого стенда.
  Прежнее имя атрибута оставлено фолбэком. Юнит-тесты этот атрибут не мокали
  вовсе — найдено живой приёмкой IIS 17.08.2026.
- **IIS: `state:Unknown` больше не считается «сайт остановлен».** При
  остановленных службах IIS `appcmd` отдаёт `Unknown` — то есть «сам не знаю».
  Раньше вердикт был `DOWN` с причиной «сайт остановлен (state=Unknown)», то
  есть сломанный канал управления выглядел как штатно погашенный стенд. Теперь
  это неопределённое состояние: вердикт по TCP-порту, а причина прямо называет
  остановленные службы («состояние не выяснено: остановлены службы IIS (WAS,
  W3SVC)»).
- **IIS: ошибка «объект не найден» не выдаётся за нехватку прав.** Список
  признаков elevation был слишком широким (`error ( message:` ловил ЛЮБУЮ
  ошибку appcmd, а код 1168 — это `ERROR_NOT_FOUND`, не отказ в доступе):
  elevated-диспетчер на несуществующем сайте получал совет «запустите от имени
  администратора». Теперь признаки узкие, а «любая ошибка = права» применяется
  только когда процесс действительно НЕ elevated (`IsUserAnAdmin`).
- **IIS: остановка пула больше не падает по таймауту.** `appcmd stop apppool`
  ждёт завершения рабочего процесса, а IIS отводит на это `shutdownTimeLimit`
  (по умолчанию 90 секунд) — общий таймаут внешних команд 20 секунд был мал:
  живьём остановка пула прогретого стенда BPMSoft (.NET Framework) заняла
  20.6 с, диспетчер рапортовал ошибку на штатной операции. У изменяющих
  операций IIS (start/stop/recycle сайта и пула) теперь свой таймаут
  `_IIS_LIFECYCLE_TIMEOUT` = 120 секунд; читающие пробы состояния остались
  быстрыми (дашборд опрашивает их часто).
- **IIS: логи стенда читаются из подпапок-дат.** BPMSoft под .NET Framework
  пишет `Logs\<ГГГГ_ММ_ДД>\Application.log`, в корне каталога `*.log` нет вовсе —
  `read_logs` возвращал `None`, и консоль стенда в диспетчере оставалась пустой
  при живых файлах лога. Плоские логи (kestrel) по-прежнему в приоритете.
- **Остановленный стенд больше не показывается работающим.** Общее правило для
  всех бэкендов хостинга: ответ CLI авторитетнее открытого TCP-порта, фолбэк на
  порт применяется только там, где состояние выяснить не удалось (утилита не
  найдена, команда упала, вывод не разобран). Раньше это правило действовало
  только для IIS; живая приёмка на настоящих Docker и Kubernetes 17.08.2026
  показала два его нарушения:
  - **k8s:** после `stop` (scale 0) `kubectl` честно отвечал «готовых реплик
    нет» — пустой `status.readyReplicas`, — но вердикт перебивался открытым
    NodePort, который слушается всё время, пока существует Service. Стенд
    отображался живым, а сводный статус выходил противоречивым:
    `process=ok, http=down`. Теперь пустой ответ при rc=0 трактуется как
    определённое «не запущен»; нечисловой ответ по-прежнему считается
    неопределённостью и уходит в фолбэк.
  - **docker:** состояние контейнера при `rc=0` теперь окончательное, порт его
    не переопределяет. Заодно вместо `.State.Running` спрашивается
    `.State.Status`: у приостановленного контейнера (`docker pause`)
    `Running=true`, хотя он не обслуживает запросы, — такой стенд показывался
    зелёным.
- **compose-режим больше не путает сервисы с похожими именами.** `is_running`
  сопоставлял имя сервиса как подстроку любой строки `docker compose ps`:
  при поднятом `webhook` неподнятый `web` считался запущенным. Теперь
  используется машиночитаемый `docker compose ps --format json` с точным
  сравнением поля `Service`, а на версиях compose без этого формата —
  табличный вывод с разбором по токенам, а не по подстроке.

### Прочее
- Докстринг `HostKind.K8S` больше не утверждает, что логики k8s ещё нет — она
  есть с 0.5.0 (ADR-0002) и прошла живую приёмку.
- `docs/BACKLOG.md`: раздел приёмки актуализирован, добавлены остатки, найденные
  живым прогоном, и рецепт воспроизводимого k8s-контура на Windows с cgroup v1.

## [0.6.1] — 2026-07-27

### Исправлено
- **Повторный запуск по ярлыку больше не поднимает второй диспетчер.** Ярлык
  стартует хаб через `pythonw.exe`, окна нет, а закрытие браузера процесс не
  останавливает — idle-shutdown у хаба нет. Поэтому второй клик по ярлыку
  запускал ещё один экземпляр: два фоновых поллера дёргали health-пробы и
  внешние команды бэкендов хостинга над одним `projects.json`, а окно
  открывалось на другом origin со своей копией localStorage (сбрасывалась
  тема). На Windows было хуже, чем предполагалось: из-за `SO_REUSEADDR` bind
  на уже слушаемый 8770 проходил успешно, и два хаба молча делили один порт.
  Теперь перед стартом проверяется, не работает ли диспетчер уже — если да,
  просто открывается браузер на нём. Откат на свободный порт сохранён для
  случая, когда 8770 занял чужой сервис.
- **Дашборд честно сообщает, что диспетчер остановлен.** Раньше вкладка с
  умершим хабом продолжала показывать последний снапшот как живой, а
  единственными признаками были красная точка в углу и браузерное
  `Failed to fetch` в тостах. Теперь показывается баннер с объяснением и тем,
  что делать, устаревшая таблица гасится, а сетевые ошибки и 401 («сессия не
  подтверждена» после перезапуска диспетчера) переведены на понятный язык.

## [0.6.0] — 2026-07-27

### Добавлено
- **Усыновление стендов, поднятых вне диспетчера.** Стенд, запущенный руками
  (`dotnet BPMSoft.WebHost.dll` из консоли, скриптом, чужой сессией), теперь
  можно остановить и перезапустить: диспетчер находит владельца порта,
  проверяет, что это действительно процесс ЭТОГО стенда (порт + имя образа из
  allowlist + рабочий каталог внутри `stand_dir`), и берёт его под управление —
  **только с явного подтверждения**. Без подтверждения процесс не трогается.
  В таблице стендов появился бейдж «вне диспетчера».
- **IIS: автоопределение сайта** по physical path и биндингу для стенда,
  развёрнутого мимо диспетчера; снятие зависшего `w3wp` по pid; различение
  состояний «сайт остановлен» / «пул остановлен» / «порт держит http.sys».
- **PWA.** `manifest.webmanifest` + иконки: Chrome и Edge предлагают
  «Установить приложение» — дашборд получает отдельное окно без адресной
  строки, свою иконку в панели задач и место в Alt+Tab. Зависимостей не
  добавилось.
- **Компактный режим** `?view=compact` — узкое окно-виджет: имена стендов,
  состояния и старт/стоп. Доступен ярлыком из установленного PWA.
- `GET /api/stands?probe=0` — слепок реестра без сетевых проб, и
  `GET /api/events` — SSE-поток обновлений состояния.

### Изменено
- **Дашборд открывается мгновенно.** Раньше первый экран ждал полного обхода
  всех стендов: пробы шли последовательно, до 9 секунд на стенд, а конфиг и
  реестр перечитывались с диска на каждый запрос. Три недоступных стенда за
  firewall давали около 27 секунд серого экрана. Теперь состояние собирает
  фоновый поток, а страница рисуется сразу и обновляется по мере готовности.
- **Фиксированный порт по умолчанию — 8770** (с откатом на свободный, если
  занят). Побочный эффект прежнего эфемерного порта: браузер каждый запуск
  считал дашборд новым сайтом, из-за чего сбрасывалась выбранная тема и
  заново качалась статика.
- Тема хранится в конфиге хаба и применяется до загрузки скриптов — тёмная
  больше не мигает светлой при открытии.
- Настройка «интервал автообновления» наконец работает: раньше значение из
  формы ни на что не влияло, интервал был жёстко зашит.
- **Форма настроек разгружена**: сразу видны четыре основных поля, параметры
  федерации и демона-агента убраны под спойлеры, причём блок агента скрыт
  целиком, пока в реестре нет удалённых стендов. У полей появились пояснения
  и подсказки со значениями по умолчанию.
- Остановка стенда стала мягкой: сначала штатное завершение с ожиданием и
  только потом принудительное — стенд успевает закрыть соединения с БД и
  Redis. Раньше на Windows сразу шёл `taskkill /T /F`.
- Статика отдаётся с валидаторами кэша (`ETag`, `304`).

## [0.5.2] — 2026-07-25

### Изменено
- **IIS: жизненный цикл по Site.** Стоп/рестарт/детект работают по **Site**
  стенда; **App Pool не трогаем** (может быть общим с другими приложениями).
  App Pool задействуется только когда `iis_site` не задан. Детект «жив» — по
  состоянию сайта; открытый TCP-порт больше не маскирует остановленный сайт
  (http.sys держит порт). См. [ADR-0004](adr/0004-iis-site-scoped-lifecycle.md).
- **Читаемые ошибки внешних команд.** Вывод `appcmd`/`docker`/`kubectl`
  декодируется utf-8 → OEM (cp866) → cp1251 — больше не «кракозябры».
- **Хаб — тяжёлые логи IIS.** Панель «Текущее состояние» берёт логи только за
  сегодня и читает лишь хвост файла (до 4 МБ) — дневной IIS-лог в сотни МБ не
  грузится целиком.
- Упаковка: SPDX-выражение лицензии (`license = "MIT"`, `license-files`) —
  убран deprecation-warning setuptools.

### Добавлено
- Подсказка «запустите диспетчер от имени администратора» при ошибках `appcmd`
  из-за нехватки прав (IIS требует elevation).
- Кнопка «Обновить» даёт обратную связь (блокировка + «Обновление…» + время).
- Колонка **Redis** в таблице стендов с номером базы.
- Обратная связь и надёжность первого запуска: папка реестра создаётся при старте
  диспетчера и при первой записи.

### Исправлено
- **Честный отказ** при остановке стенда, запущенного вне диспетчера (нет
  pidfile): вместо мнимого «остановлено» — понятная ошибка.
- Логи стенда ищутся в подпапках по датам (рекурсивный листинг) — раньше хаб
  ошибочно сообщал «в каталоге нет файлов».
- Модалки не закрываются при выделении текста мышью с отпусканием за краем окна.
- Колонки таблицы не «прыгают» при смене статуса; HTTP-значение — кликабельная
  ссылка; кнопки в модалках не слипаются.
- `Ctrl+C` завершает `standkit-hub` чисто, без трейсбека `KeyboardInterrupt`.
- Дедуп SVG-ассетов; TODO-докстринги урезаны до ссылок на документацию/бэклог.
