# Трек исследования: companion v2 — CI/CD через тонкого агента

- **Статус:** заявка на исследование, решения не приняты
- **Заведено:** 18.08.2026, по итогам живого прогона развёртывания агента на Linux
- **Горизонт:** после 0.7.x, не раньше чем закроются GAP-001…GAP-007

Документ фиксирует, что уже есть, какие развилки придётся пройти и в каком
порядке их дешевле проверять. Это не план работ и не обещание функциональности.

## 1. Что уже есть в 0.7.0

Агент — headless-демон на stdlib с узким HTTP-контрактом: `stands`, `status`,
`logs`, `start`, `stop`, `restart`, `adopt`. Полезное для темы CI/CD:

- **два скоупа** (`control` / `readonly`) на уровне токена — деплой-конвейеру
  можно выдать отдельный токен;
- **аудит append-only** в JSON lines: `ts`, `src_ip`, `identity`, `path`,
  `result`, `code` — готовая основа для журнала выкатов;
- **честные отказы**: `409 adopt_required` вместо молчаливого убийства чужого
  процесса — тот же принцип понадобится для «стенд занят выкатом»;
- **бэкенды хостинга** (kestrel / iis / docker / k8s) уже абстрагированы —
  перезапуск после выката не придётся писать заново для каждой площадки;
- **fail-closed на транспорте**: loopback без TLS, отказ стартовать наружу без
  сертификата.

Чего нет: доставки артефактов, применения изменений (пакеты, миграции БД),
понятия «версия стенда», отката, очереди задач и долгих операций — весь
контракт синхронный и быстрый.

## 2. Главная развилка: где живёт логика деплоя

standkit — бесплатный диспетчер стендов; провижининг и деплой исторически
относятся к платному BPMkit. Отсюда три варианта, между которыми надо выбрать
до любой реализации.

| Вариант | Агент умеет | Плюсы | Минусы |
|---|---|---|---|
| **A. Тонкий транспорт** | принять артефакт, выполнить *заранее описанный на хосте* рецепт, вернуть статус | граница «бесплатное/платное» не размывается; агент остаётся аудируемым и маленьким | рецепты надо где-то поддерживать; шаг вправо — и это уже удалённый shell |
| **B. Агент со сценариями** | знает про пакеты BPMSoft, миграции, прогрев | цельный продукт из коробки | агент перестаёт быть тонким; тянет знание о платформе в бесплатный слой |
| **C. Только наблюдатель** | сообщает состояние, деплой делает внешний раннер на хосте | минимум риска; агент не растёт | ради чего тогда companion — ценность близка к нулю |

Рабочая гипотеза — **A**, с жёстким инвариантом: агент не выполняет произвольные
команды, только именованные рецепты, зарегистрированные на хосте вне канала
управления. Иначе `POST /deploy` превращается в удалённый shell с Bearer-токеном.

## 3. Что придётся спроектировать

1. **Долгие операции.** Текущий контракт синхронный. Выкат — минуты: нужен
   `202 Accepted` + `job_id`, `GET /job/<id>`, хвост лога, отмена. Это первый
   реальный слом существующей модели.
2. **Идемпотентность и параллелизм.** Повтор запроса от CI после таймаута не
   должен приводить ко второму выкату; одновременные выкаты на один стенд —
   отклонять по образцу `adopt_required` («стенд занят задачей X»).
3. **Доставка артефакта.** Загрузка через агента (лимиты тела, диск, проверка
   контрольной суммы) против «агент сам забирает из хранилища по ссылке».
   Второе снимает с агента приём больших файлов, но требует доступа хоста к
   артефакторию и обращения с его секретом.
4. **Версия стенда.** Сейчас `last_deploy: unknown` — это заглушка. Без
   надёжного «что сейчас на стенде» ни откат, ни отчётность не построить.
5. **Откат.** Что именно откатывается: файлы стенда, пакеты платформы, схема
   БД? Для БД честный ответ, скорее всего, «не откатываем, только резервная
   копия до выката» — и это надо сказать прямо, а не подразумевать.
6. **Права.** Выкат требует записи в каталог стенда и рестарта — то есть прав
   шире, чем у нынешнего наблюдателя. Отдельный скоуп `deploy`, отдельный
   токен, отдельная запись в аудите.

## 4. Риски

- **Расширение RCE-поверхности.** Сегодня агент управляет ровно тремя
  глаголами над известным процессом. Деплой добавляет запись на диск —
  компрометация токена становится существенно дороже. Митигация: отдельный
  скоуп, mTLS обязателен для `deploy`, рецепты только из локального каталога с
  правами root.
- **Секреты CI.** Токен агента в переменных сборки — типовой путь утечки.
  Смотреть в сторону короткоживущих токенов и/или клиентских сертификатов на
  раннера, а не постоянного Bearer.
- **Расползание бесплатного слоя.** Каждая уступка в сторону варианта B
  усложняет разграничение с платным продуктом. Нужен явный список того, чего
  агент не делает никогда.
- **Долгие операции ломают модель отказов.** Синхронный «честный отказ»
  превращается в состояние; появляются зависшие задачи, дубликаты, гонки.

## 5. Порядок проверки (дёшево → дорого)

1. **Бумажный прототип контракта**: `POST /stand/<имя>/deploy` (рецепт + версия
   артефакта) → `202` + `job_id`, `GET /job/<id>`. Проверить на трёх реальных
   сценариях, не выходя за границы варианта A.
2. **Спайк «долгая операция»** на существующем коде: очередь на одну задачу,
   `job_id`, хвост лога. Проверить, что модель отказов не сломалась.
3. **Спайк доставки**: заливка артефакта с контрольной суммой против забора по
   ссылке — измерить время, потребление диска, поведение на обрыве.
4. **`last_deploy` по-настоящему**: откуда брать версию стенда для каждого
   `host_kind`. Без этого пункты 1–3 остаются демонстрацией.
5. Только после этого — решение по варианту A/B/C и постановка в ROADMAP.

## 6. Что считать успехом трека

Исследование закрыто, когда есть: выбранный вариант с обоснованием, описанный
контракт долгих операций, честный список того, чего агент не делает, и оценка
трудоёмкости варианта A в неделях. Отрицательный результат («companion v2 не
нужен, достаточно варианта C») — тоже закрытие.
