# GAP-006 — каталог логов ищется как `logs` и путями хоста хаба

- **Область:** просмотр логов (хаб), бэкенд IIS
- **Приоритет:** высокий
- **Заведён:** 18.08.2026
- **Статус:** ✅ закрыт — 0.8.0, PR #34
- **Как закрыт:** резолв вынесен в `standkit/logs.py`
  (`find_logs_subdir` / `stand_logs_dir`): имя подкаталога сравнивается по
  `casefold()` через `os.scandir`, точное совпадение регистра в приоритете —
  никакой жёсткой замены `"logs"` → `"Logs"`. Общей функцией пользуются и
  `standkit_hub/logs_browser.py`, и `IisBackend.read_logs`. Добавлено поле
  реестра `logs_dir` для нестандартной раскладки. Пути POSIX-стендов
  форматируются через `PurePosixPath` — обратных слэшей в сообщениях больше
  нет. Для `transport=agent` вместо «каталог не найден» выводится
  `logs_unavailable_reason`: каталог живёт на хосте стенда, локально хаб его
  не видит. Фиксы Windows/IIS (подпапки-даты, `iis_stdout_log_dir`,
  рекурсивный обход) не тронуты — регрессионные тесты зелёные.

## Симптом

Панель «Текущее состояние» для стенда на Linux показывает:

```
лог недоступен (источник «Стенд»: каталог не найден — \mnt\composers\bpmsoft\stand-a\app\logs)
```

При этом каталог существует — но называется `Logs` (с заглавной), а путь в
сообщении собран с обратными слэшами, хотя это POSIX-хост.

Два независимых дефекта в одном сообщении:

1. **Регистр.** BPMSoft раскладывает логи в `Logs`. Windows-файловая система
   регистронезависима, поэтому на Windows жёсткое `"logs"` попадает в `Logs`
   и всё работает; на Linux `Path(...)/"logs"` не существует → «каталог не
   найден».
2. **Разделитель.** Путь удалённого (POSIX) стенда собирается `pathlib.Path`
   на машине хаба под Windows, то есть `WindowsPath`, и в сообщение уезжает
   `\mnt\composers\…`. Даже когда путь верный, оператор видит бессмысленную
   строку и ищет ошибку не там.

## Почему так

Имя каталога зашито строкой в двух местах:

- `standkit_hub/logs_browser.py::raw_logs_path` — `Path(stand.stand_dir) / "logs"`
  (и симметрично для источника `bpmkit`: `<docs_folder>/logs`);
- `standkit/hosting.py::IisBackend.read_logs` — `Path(stand.stand_dir) / "logs"`,
  когда не задан `iis_stdout_log_dir`.

Отдельно: для стенда с `transport=agent` каталог логов резолвится **на стороне
хаба** (`resolve_logs_dir` проверяет `p.exists()` локально), хотя путь описывает
файловую систему удалённого хоста. На Windows-хабе такой путь не существует
никогда — сообщение «каталог не найден» технически верно и полностью
бесполезно.

## Что сделать

⚠️ **Не сломать то, что уже починено на Windows.** В этом коде живут два
рабочих фикса, оба вскрыты живой приёмкой IIS 17.08.2026:

- логи BPMSoft под .NET Framework лежат в подпапках-датах
  (`Logs/2026_08_17/Application.log`), и `IisBackend.read_logs` после плоского
  `glob("*.log")` делает фолбэк на `glob("*/*.log")`;
- `list_log_files` обходит каталог рекурсивно по той же причине;
- приоритет `iis_stdout_log_dir` над каталогом по умолчанию.

Всё это должно остаться нетронутым.

1. Резолвить имя каталога **по факту**, а не по константе: перебрать записи
   `stand_dir` через `os.scandir` и взять первую директорию, чьё имя совпадает
   с `logs` по `casefold()`. На Windows результат не меняется (там `logs` и так
   попадает в `Logs`), на Linux — находится `Logs`, `LOGS` и любой другой
   регистр. Никакой жёсткой замены `"logs"` → `"Logs"`: она сломает контуры,
   где каталог действительно в нижнем регистре.
2. Вынести резолв в одну функцию (`standkit/logs.py` или `logs_browser`), чтобы
   хаб и `IisBackend` пользовались общей логикой, а не двумя копиями строки.
3. Разрешить явное переопределение через реестр — поле `logs_dir` (по образцу
   уже существующего `iis_stdout_log_dir`), чтобы нестандартную раскладку можно
   было задать без правки кода.
4. Для agent-стендов не показывать «каталог не найден» по локальной проверке:
   либо спрашивать путь у агента, либо честно писать «каталог логов проверяется
   на хосте стенда; локально хаб его не видит».
5. Пути удалённых стендов форматировать через `PurePosixPath` (или просто не
   пропускать через `Path` при выводе), чтобы в сообщениях не появлялись
   обратные слэши на POSIX-хостах.

## Критерий приёмки

- Linux-стенд с каталогом `Logs` открывает логи из дашборда; Windows/IIS-стенд
  (в том числе с подпапками-датами и с `iis_stdout_log_dir`) продолжает работать
  ровно как сейчас — регрессионные тесты `tests/test_hosting.py` зелёные.
- В сообщении «каталог не найден» путь POSIX-стенда отображается с прямыми
  слэшами.
- Есть тест на регистр имени каталога, выполняющийся и на Windows, и на Linux
  (на регистронезависимой ФС он проверяет отсутствие регрессии, на Linux —
  собственно фикс).
