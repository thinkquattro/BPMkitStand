# GAP-008 — дашборд не может доверять самоподписанному сертификату агента

- **Область:** хаб (клиент агента), реестр, TLS
- **Приоритет:** высокий
- **Заведён:** 18.08.2026 (живая проверка контура «дашборд ↔ агент» между машинами)
- **Статус:** ✅ закрыт — 0.8.0 (не выпущено), PR #PRNUM
- **Как закрыт:** в `Stand` добавлены `agent_ca` (путь к сертификату/CA агента
  на машине дашборда) и `agent_verify_tls` (по умолчанию `true`);
  `standkit_hub/client.py::_build_agent_ssl_context` строит контекст явно —
  `ssl.create_default_context(cafile=…)`, а снятие проверки действует только
  для `https://`-адресов, по образцу `health.http_probe`. Ошибка
  `CERTIFICATE_VERIFY_FAILED` больше не показывается как «агент недоступен»:
  различаются недоверенный CA, несовпадение имени с CN/SAN и ненайденный файл
  `agent_ca`, у каждого свой рецепт. Оба поля есть в форме регистрации и в
  `projects.sample.json`. `SSL_CERT_FILE` остался в документации только как
  исторический обходной путь.

## Симптом

Оператор поднял агента с TLS по инструкции: сертификат выпущен самоподписанным,
`curl --cacert agent.crt` с той же машины работает, `/stands` и `/status`
отвечают. В реестре оператора запись переведена на `transport=agent`. Дашборд
показывает стенд недоступным:

```
RemoteCallError: Ошибка обращения к агенту https://example-host:8765:
<urlopen error [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed:
self-signed certificate (_ssl.c:1077)>
```

Ни одна из настроек реестра ситуацию не меняет: `verify_tls` относится к пробе
СТЕНДА, а не к каналу до агента, и оператор, найдя это поле, обоснованно
считает, что уже отключил проверку.

## Почему так

1. `standkit_hub/client.py::_agent_request` вызывает `urllib.request.urlopen`
   без `context`, то есть со штатным `ssl.create_default_context()`: цепочка
   проверяется по системному хранилищу. Это правильное поведение по умолчанию —
   проблема в том, что у него нет управляемого исключения.
2. У записи стенда есть пара `stand_scheme` / `verify_tls` для пробы стенда, но
   для канала «хаб → агент» аналога (`agent_ca` / `agent_verify_tls`) нет.
   Симметрия нарушена, и это сбивает.
3. Единственный обходной путь — переменная окружения `SSL_CERT_FILE`, заданная
   ДО запуска процесса (после импорта `ssl` она уже не действует). Нигде не
   задокументировано.
4. Инструкция по агенту предлагает самоподписанный сертификат как штатный
   вариант первого развёртывания — то есть в этот гэп попадает каждый, кто
   доходит до TLS.

## Что сделать

1. Добавить в запись реестра поле `agent_ca` (путь к сертификату/CA агента) и,
   отдельным осознанным флагом, `agent_verify_tls` (по умолчанию `true`).
   Передавать их в `_agent_request` через явный `ssl.create_default_context(
   cafile=...)`, по образцу того, как это сделано в `health.http_ok`.
2. Ошибку `CERTIFICATE_VERIFY_FAILED` показывать в интерфейсе не как «агент
   недоступен», а отдельным диагнозом с рецептом: «сертификат агента не
   доверенный — укажите `agent_ca`».
3. До реализации — задокументировать `SSL_CERT_FILE` (сделано в
   [COOKBOOK_LINUX.md](../COOKBOOK_LINUX.md), раздел 10.2).
4. В форме регистрации стенда дашборда предусмотреть поля агента вместе с
   [GAP-001](GAP-001-registry-fields-out-of-hub-form.md).

## Критерий приёмки

Оператор, выпустив самоподписанный сертификат агента по кукбуку, подключает
стенд из дашборда без правки переменных окружения: указывает `agent_ca` в
записи реестра и видит статус. Попытка подключиться к агенту с неизвестным
сертификатом без явного разрешения по-прежнему завершается отказом с понятным
текстом.
