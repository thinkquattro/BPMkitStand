# GAP-002 — `http: down` не объясняет причину, а обновление версии не меняет поведения

- **Область:** health-пробы, UX дашборда
- **Приоритет:** высокий
- **Заведён:** 18.08.2026 (живая приёмка агента на Linux)
- **Статус:** ✅ закрыт — 0.8.0, PR #34
- **Как закрыт:** `standkit/health.py` получил `HttpProbeResult` и `http_probe()`;
  `http_ok()` сохранена как тонкая обёртка (прежний публичный API). Причина
  отказа распознаётся (отказ соединения, таймаут, DNS, TLS-рукопожатие,
  непрошедший проверку сертификат, 5xx, «ответ не по протоколу HTTP») и
  кладётся в `StandStatus.details["http_reason"]` вместе с фактическим URL —
  по образцу `process_reason`. Главный случай сопровождается подсказкой
  «похоже, стенд за TLS: задайте stand_scheme=https (и verify_tls=false для
  self-signed)». Заодно в перехват добавлен `http.client.HTTPException`:
  `BadStatusLine` раньше вылетал из пробы наружу. Автодетект схемы
  сознательно НЕ делался — по разбору из п. 3 ниже. Дашборд показывает причину
  подсказкой к ячейке (пунктирное подчёркивание = причина есть).

## Симптом

Оператор видит `http: down` при живом стенде. Обновляет пакет до версии, в
которой дефект HTTPS-пробы «закрыт», перезапускает агента — и получает ровно тот
же `down`. Дальше он обоснованно считает, что фикс не работает.

Фактически фикс работает: 0.7.0 добавила **поля реестра**, а дефолты
(`stand_scheme="http"`, `verify_tls=True`) намеренно повторяют прежнее
поведение. Пока поля не выставлены — ничего не меняется, и об этом нигде не
сказано.

## Почему так

1. `_probe_http` (`standkit/health.py`) возвращает голый
   `ProbeState.DOWN` — без текста причины. Различить «порт закрыт», «TLS-ошибка»,
   «таймаут» и «сервер ответил 5xx» по дашборду невозможно. `http_ok` при этом
   намеренно глотает исключения (`URLError`, `TimeoutError`, `OSError`,
   `ValueError`) — это правильно для пробы, но диагноз теряется вместе с ними.
2. У пробы процесса такой механизм уже есть: `describe_state` кладёт
   человекочитаемую причину в `StandStatus.details["process_reason"]`, и витрина
   показывает диагноз вместо мигающего индикатора. Для HTTP аналога нет.
3. Обновление версии не сопровождается ни миграцией записей реестра, ни
   подсказкой «у стенда включён TLS, а схема пробы — `http`».

## Что сделать

1. Складывать причину отказа HTTP-пробы в `StandStatus.details["http_reason"]`
   (по образцу `process_reason`): текст исключения без секретов и без тела
   ответа, плюс фактический URL, по которому стучались.
2. Отдельно распознать самый частый случай: `SSLError` / отказ на `http://` при
   TLS-порте → подсказка «похоже, стенд за TLS: задайте `stand_scheme=https`
   (и `verify_tls=false` для self-signed)». Это дешевле полноценного автодетекта
   и не меняет семантику пробы.
3. Решить отдельно, нужен ли **автодетект схемы** (проба `https` после неудачи
   `http`). Плюс — «работает из коробки»; минусы: удвоенное время пробы на
   реально мёртвом стенде, два запроса на каждый цикл поллера, риск молча
   ходить в TLS без проверки сертификата. Предложение: не делать автодетект
   по умолчанию, ограничиться подсказкой из п. 2 и настройкой из
   [GAP-001](GAP-001-registry-fields-out-of-hub-form.md).
4. В `docs/CHANGELOG.md` для изменений такого рода явно писать строку
   «требуется действие оператора» — фикс, включаемый полем реестра, без этой
   пометки читается как автоматический.

## Критерий приёмки

На стенде за TLS без выставленных полей дашборд показывает не просто `down`, а
причину и конкретную рекомендацию; после выставления полей — `ok`. Оператор
доходит до решения без чтения исходников.
