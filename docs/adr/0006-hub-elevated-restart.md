# ADR-0006 — Права администратора для IIS: перезапуск диспетчера через UAC и однократная операция

- Статус: **Принято / реализовано** (v0.11.0, GAP-311, 15.09.2026). Первая версия
  перезапуска написана 19.08.2026 в ветке `feat/hub-elevated-restart` (тогда под номером
  ADR-0005, который к мержу оказался занят ADR о канале обновлений), перенесена в
  `main` с доработками по двум раундам ревью.
- Контекст-владелец: Владимир Терновский
- Связано: [ADR-0004](0004-iis-site-scoped-lifecycle.md) (диагноз «нехватка прав» у `appcmd`),
  [HOSTING.md](../HOSTING.md); в dev-репо BPMkit — GAP-282 (путь без прав: перезапуск
  приложения сменой `LastWriteTime` у `web.config`) и GAP-311.

## Контекст и проблема

Управление стендами IIS идёт через `appcmd.exe`, а он без прав администратора не работает
в принципе: не читает даже `…\inetsrv\config\redirection.config`. Диспетчер честно называл
причину и советовал «запустите standkit-hub с правами администратора», но выполнить совет
было нельзя:

1. Ошибка остановки IIS-стенда с подсказкой про права.
2. Пользователь запускает ярлык «от имени администратора».
3. Ничего не меняется: новый процесс видит на порту 8770 работающий диспетчер
   (single-instance, `HubAlreadyRunning`), открывает браузер на СТАРОМ — без прав — и выходит.

Живьём воспроизведено дважды: 19.08.2026 и 15.09.2026 (`TokenIsElevated=0` у работающего
`pythonw -m standkit_hub`, хотя пользователь уверен, что запускал от администратора).

## Решение

### 1. Видно, что прав нет

`GET /api/hub/elevation` → `{supported, elevated, can_restart, reason, user, restart}`.
Щит «без прав администратора» в шапке показывается **только когда прав нет** (решение
владельца). С правами и на не-Windows щита нет; состояние прав всегда видно в
«Настройки → О программе». Ошибка действия со стендом при нехватке прав приходит с
признаком `elevation_required: true`, и в сообщении две кнопки — «Перезапустить с правами
администратора» и «Только эту операцию».

### 2. Перезапуск диспетчера с правами (П1)

`POST /api/hub/restart-elevated`:

```
старый хаб                                   новый хаб (runas, --takeover)
──────────                                   ─────────────────────────────
restart=requesting (под lock)
handoff-файл с токеном сессии
ShellExecuteW runas ──UAC «Нет»──> 409 cancelled, restart=null, handoff удалён
         │ «Да»
202, restart=pending,                        1. SID != --initiator-sid → result: refused, выход
наблюдатель result-файла                     2. читает handoff (одноразово)
         │                                   3. пишет stop-request (pid старого)
stop-request для моего pid ───────────────── 4. ждёт освобождения порта
штатный shutdown, выход                      5. bind СТРОГО на тот же порт (повторы)
(дочерние стенды и агент живут)              6. result: serving | failed (+причина)
```

- Старый процесс завершается **только** по stop-request — не «через секунду после 202».
  Отказ под другой учётной записью, сбой перехвата или таймаут оставляют старый
  диспетчер работать, а причина видна в `restart.status` = `refused` / `failed`.
- Если stop-request проигнорирован (зависший хаб), эскалация завершает **только сам pid**
  (`taskkill` без `/T`): стенды Kestrel и локальный агент — дочерние процессы хаба и не
  должны умирать вместе с ним. Перед эскалацией личность процесса подтверждается у ОС
  (время создания процесса против записанного в файле состояния; маркер в командной
  строке — только когда время создания получить нельзя). Не подтверждено — не убиваем,
  отдаём «остановите вручную».
- Сессия переезжает одноразовым файлом передачи (TTL 3 минуты, удаляется при чтении),
  не аргументом командной строки. Открытая вкладка переподключается сама.
- Запуск ярлыка «от имени администратора» при живом неэлевированном экземпляре идёт тем
  же путём перехвата (stop-request, строгий bind).
- Перезапуск учитывает поставку: во frozen-сборке (`BPMkit-hub.exe`) запускается
  `sys.executable`, в режиме `--desktop` новый процесс открывает своё окно, а старое
  закрывается по stop-request. Передаются `--host`/`--insecure`, абсолютный `--config`.
- Права держатся до выхода диспетчера; обратного перехвата (elevated уступает обычному) нет.

### 3. Однократная операция с правами (П2)

`POST /api/hub/elevated-op {stand, action}` запускает через UAC тот же исполняемый файл в
режиме `--elevated-op start|stop|restart --stand <имя> --result-file <путь>`: одна операция
над стендом `host_kind=iis`, без HTTP-сервера, мьютекса и файла состояния, результат в файл,
выход. Диспетчер остаётся без прав. `GET /api/hub/elevated-op/<op_id>` —
`pending` / `ok` / `error` / `refused` / `expired`. Одна активная операция на стенд.

### 4. Повышение под другой учётной записью — отказ с пояснением

Если окно UAC подтвердил другой пользователь (over-the-shoulder), у нового процесса другой
профиль: другой `projects.json`, конфиг, ключи. Работать от его имени — значит молча
показать пустой реестр или чужие секреты. Новый процесс сравнивает SID своего токена с
`--initiator-sid` и при расхождении ничего не делает, записывая текст: «Права подтверждены
другой учётной записью (…). Диспетчер работает с реестром стендов и ключами текущего
пользователя Windows, поэтому повышение под другой учётной записью не поддерживается. …»

### 5. Мьютекс диспетчера

Именованный мьютекс (GAP-229/284) берётся после bind. Созданный elevated-процессом объект
получил бы DACL «только администраторы», и неэлевированный установщик BPMkit не увидел бы
работающий диспетчер. Поэтому мьютекс создаётся с явным security descriptor
(SYSTEM, Администраторы, текущий пользователь — полный доступ; Everyone — SYNCHRONIZE).

## Модель угроз

- Сторонний сайт не может запросить UAC или операцию: все новые мутации — `POST` с
  CSRF-заголовком, локальным `Origin` и сессионным токеном; `stand`/`action`/`op_id`
  валидируются белыми списками и регулярными выражениями.
- **UAC — не граница безопасности** (позиция Microsoft). Процесс той же учётной записи
  без прав может править конфиг и реестр стендов, которые затем прочитает elevated-процесс.
  Мы это принимаем: согласие в окне UAC даётся на диспетчер, работающий с данными этого
  пользователя. Что сделано против дешёвых приёмов: elevated-процесс не пишет в `run_dir`
  и не читает оттуда, если путь или файл — reparse point/symlink; временные файлы — со
  случайным именем и `O_EXCL`; однократная операция повторно проверяет `host_kind=iis`.
- Права `0o600` на Windows ACL не задают — защиту файла передачи обеспечивает ACL профиля.
  `run_dir` вне профиля пользователя даёт предупреждение в логе.

## Последствия

- Ошибка прав для IIS решается кнопкой в два клика и видна до первой неудачной операции.
- Отказ в UAC, чужая учётка, зависший старый процесс — у каждого свой понятный исход,
  пользователь не остаётся без диспетчера.
- Живая приёмка возможна только на Windows с IIS и настоящим окном UAC; юнит-тесты
  покрывают протокол, но не WinAPI.

## Альтернативы, которые не выбрали

- **Только однократная операция на каждое действие.** Минимальные права, но окно UAC на
  каждый старт/стоп в ежедневной работе неприемлемо — оставлена как дополнительный путь (П2).
- **Галка «Запуск от имени администратора» в свойствах ярлыка.** Лечит только будущие
  запуски, не ситуацию «диспетчер уже открыт». Осталась рекомендацией в HOSTING.md.
- **Задача планировщика «с наивысшими правами» из установщика.** Отклонена владельцем
  14.09.2026 как избыточная.
- **Служба Windows.** Другой класс задачи (автозапуск, своя учётка); для удалённых
  IIS-стендов вопрос остаётся открытым в dev-репо (GAP-282, §3.1 записки).
