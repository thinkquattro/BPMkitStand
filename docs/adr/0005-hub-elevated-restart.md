# ADR-0005 — Перезапуск диспетчера с правами администратора (UAC) из дашборда

- Статус: **Принято / реализовано** (2026-08-19)
- Контекст-владелец: Владимир Терновский
- Связано: [ADR-0004](0004-iis-site-scoped-lifecycle.md) (диагноз «нехватка прав» у `appcmd`), [HOSTING.md](../HOSTING.md)

## Контекст и проблема

Управление стендами IIS идёт через `appcmd.exe`, а он **без прав администратора
не работает в принципе**: не читает даже собственный
`…\inetsrv\config\redirection.config`. ADR-0004 научил диспетчер честно
называть эту причину («похоже, не хватает прав администратора: … запустите
standkit-hub с правами администратора»), но выполнить этот совет оказалось
нетривиально — приёмка 19.08.2026 на стенде `iis19`:

1. Пользователь получает ошибку остановки стенда с подсказкой про права.
2. Правым кликом запускает ярлык «BPMkit Диспетчер» **от имени администратора**.
3. **Ничего не меняется.** Новый процесс видит на порту 8770 уже работающий
   диспетчер (single-instance проверка, `probe_hub_instance`), считает свою
   работу сделанной, открывает браузер на СТАРОМ — неэлевированном —
   экземпляре и выходит. Ошибка прав повторяется, хотя пользователь уверен,
   что сделал ровно то, что просили.

Единственный способ добиться результата был неочевиден: сначала найти и
погасить фоновый `pythonw.exe` (окна у него нет), и только потом запустить
ярлык от администратора.

## Решение

Два независимых изменения — диагноз и лечение.

### 1. Single-instance теперь различает права экземпляров

Работающий диспетчер оставляет в `run_dir` файл состояния
(`standkit_hub/instance.py`: pid, host, порт, признак elevated, версия). Новый
процесс, упёршийся в занятый порт, решает по нему (`should_takeover`):

- пришёл явный `--takeover` — перехватываем (так себя перезапускает кнопка);
- **мы elevated, а работающий — нет** — перехватываем: ровно тот ручной
  сценарий «правый клик → запуск от имени администратора»;
- иначе — прежнее поведение: второй экземпляр не нужен, открываем браузер на
  работающем.

Перехват = остановить старый процесс (`standkit.platform.stop`, эскалация
«мягко → жёстко»), дождаться освобождения порта, занять его. Обратного
перехвата (elevated уступает обычному) нет намеренно: молча понижать права
работающего диспетчера — сюрприз, а не помощь.

### 2. Кнопка «Перезапустить с правами администратора»

В шапке дашборда — индикатор, который виден **только когда** ОС умеет повышать
права и сейчас их нет (`GET /api/hub/elevation`). Он же кнопка:
`POST /api/hub/restart-elevated` → `ShellExecuteW(…, "runas", …)` (единственный
штатный способ показать запрос UAC: повысить права УЖЕ запущенного процесса
нельзя) → новый процесс с `--takeover` → старый гасит себя сам через секунду
после ответа `202`.

**Сессия переезжает файлом, а не аргументом.** Новый процесс читает сессионный
токен из одноразового файла (`--session-token-file`, режим `0o600`, TTL 3
минуты, удаляется при первом чтении — даже неудачном). Поэтому уже открытая
вкладка остаётся авторизованной: её HttpOnly-cookie совпадает с токеном нового
процесса. Через argv токен не передаётся: командная строка процесса видна
всей системе (тот же контракт «секреты только ссылкой», что у
`standkit_hub.agent_control`).

Новый процесс запускается с `--no-browser` по двум причинам: вкладка уже
открыта, а браузер, порождённый elevated-процессом, сам оказался бы elevated.

## Последствия

- Ошибка прав чинится в два клика и остаётся видимой ДО первой неудачной
  операции — индикатор в шапке.
- Отказ в UAC (`ERROR_CANCELLED`, 1223) — отдельный класс ошибки
  (`ElevationCancelled`), а не «что-то пошло не так»: старый диспетчер просто
  продолжает работать. Порядок принципиален — сначала успешный запрос
  повышения прав, и только потом планирование собственного завершения, иначе
  отказ в UAC оставил бы пользователя вообще без диспетчера.
- Запущенные стенды перезапуск не трогает: диспетчер ими управляет, но не
  является их родителем.
- Локальный агент, поднятый кнопкой из хаба ДО перезапуска, остаётся жить со
  старыми правами (это отдельный процесс со своим pid-файлом). Для стендов
  IIS это неважно — их обслуживает сам хаб; агент имеет значение только для
  удалённых стендов, где вопрос прав решается на своей машине.
- На Linux/macOS кнопки нет: там «от администратора» решается службой и
  `sudo`, а не окном UAC (`elevation_supported()` → `false`, эндпоинт отвечает
  честным отказом).

## Альтернативы, которые не выбрали

- **Эскалировать каждую IIS-операцию отдельным elevated-шимом.** Права
  минимальны, но UAC-запрос на каждый старт/стоп стенда — неработоспособно в
  ежедневном режиме.
- **Просить пользователя поставить галку «Запуск от имени администратора» в
  свойствах ярлыка.** Работает, но лечит только будущие запуски и не решает
  ситуацию «диспетчер уже открыт, стенд надо поднять сейчас». Осталось как
  рекомендация в [HOSTING.md](../HOSTING.md).
- **Запускать диспетчер службой Windows.** Другой класс задачи (автозапуск,
  своя учётная запись) и другой профиль рисков; к бесплатному однопользовательскому
  диспетчеру не прилагается.
