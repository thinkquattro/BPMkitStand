# Архитектура standkit

Этот документ — краткое зеркало архитектурных решений для контекста разработки
в самом репозитории `standkit`: только то, что нужно держать перед глазами при
правке кода. Обоснования и разбор альтернатив по отдельным подсистемам —
в [adr/](adr/); дорожная карта — в [ROADMAP.md](ROADMAP.md), незакрытые заделы —
в [BACKLOG.md](BACKLOG.md).

## Модель: ядро, две оболочки и канал обновлений

```
standkit        — MIT, движок жизненного цикла, stdlib-only, без сети "наружу",
                   без лицензионно-чувствительного контента BPMSoft.
standkit_agent   — MIT, stdlib-only HTTP-обёртка вокруг ядра, кроссплатформенная
                   (Windows/Linux), разворачивается на КАЖДОМ хосте стенда.
standkit_hub     — MIT, stdlib-only локальный веб-дашборд (http.server) +
                   vanilla JS/CSS фронтенд, федеративный клиент N агентов +
                   локального ядра, ставится ТОЛЬКО на машину оператора.
                   Опциональная нативная оболочка — pywebview (extra [desktop]).
standkit_companion — MIT, stdlib-only ТРАНСПОРТ канала обновлений издателя:
                   HTTP-клиент, планировщик, проверка целостности и подписи,
                   раскладка файлов. Поднимается процессом хаба; наличие пакета
                   и есть признак редакции (ADR-0005).
```

Веб-дашборд (вариант A) заменил прежнюю PySide6/Qt-оболочку `standkit_gui`
(удалена целиком): та же роль ("диспетчер на машине оператора"), но без
тяжёлой GUI-зависимости — браузер универсален, фронтенд отдаёт сам хаб.

Границы зависимостей — принципиальны и проверяются на уровне импортов:
- `standkit/*`, `standkit_agent/*`, `standkit_hub/*` (серверная часть) и
  `standkit_companion/*` — STDLIB-ONLY, никаких сторонних веб-фреймворков/
  GUI-тулкитов. Для канала обновлений это означало отказ от `cryptography`/
  `pynacl`: проверка подписи Ed25519 написана на чистом Python
  (`standkit_companion/ed25519.py`, только `verify`).
- `standkit_hub/__main__.py` — единственное место, где опционально
  импортируется `pywebview` (только под `--desktop`, в try/except; при
  отсутствии extra `[desktop]` хаб печатает понятное сообщение и падает
  обратно в системный браузер, а не роняется исключением импорта).
- `standkit` не тянет сторонних пакетов вообще (`dependencies = []` в
  `pyproject.toml`) — секреты (`standkit/secrets.py`) используют `keyring`
  только опционально, через `try/except ImportError`.
- Фронтенд `standkit_hub/web/*` — vanilla JS/CSS, без CDN и без шага сборки
  (работает офлайн, отдаётся тем же `http.server`, что и API).

## Транспорт: `local` | `agent` (задел `ssh` / `winrm`)

Поле `transport` в записи реестра (`standkit/models.py::Transport`) определяет,
как ядро/GUI достаёт до конкретного стенда:

- `local` — стенд поднимается тем же процессом, что вызывает `standkit`
  (`standkit/lifecycle.py` поверх `standkit/platform.py`, headless-процесс
  через `subprocess`).
- `agent` — управление идёт по HTTP к `standkit_agent`, слушающему на
  `agent_url`, с Bearer-токеном, разрешаемым через `agent_secret_ref`
  (Secret-first, см. `standkit/secrets.py`).
- `ssh` / `winrm` — **схема допускает** эти значения (см.
  `projects.sample.json`, запись `example-future-ssh`), но логика НЕ
  реализована: `Stand.from_dict` толерантен к неизвестным будущим значениям
  (не роняет чтение реестра), а код, требующий конкретный транспорт
  (`lifecycle._require_local`, `client.FederatedClient._dispatch_action`),
  явно бросает `NotImplementedError`/`LifecycleError` для нереализованных
  транспортов, а не тихо делает не то.

## Кроссплатформенность

- Все пути — `pathlib.Path`, без хардкода `C:\...`.
- Запуск процесса стенда (`standkit/platform.py::spawn_hidden`) — раздельные
  ветки для `sys.platform == "win32"` (скрытое консольное окно,
  `CREATE_NO_WINDOW` + отдельная группа процессов) и POSIX
  (`start_new_session=True`, эквивалент `setsid`).
- Запуск ВНЕШНИХ КОНСОЛЬНЫХ УТИЛИТ (`appcmd`, `sc`, `docker`, `kubectl`,
  `taskkill`, `tasklist`, `powershell`) — ТОЛЬКО через
  `standkit/platform.py::run_console`, который на win32 добавляет тот же
  `CREATE_NO_WINDOW`. Прямой `subprocess.run` в остальных модулях пакета
  запрещён и стережётся тестом `tests/test_no_window.py`: у родителя без
  своей консоли (`pythonw`, служба, фоновый поллер хаба) каждый такой вызов
  рождает на экране мигающее чёрное окно, а из терминала дефект не виден
  (GAP-138: поллер опрашивал IIS-стенд парой `appcmd` раз в ~12 с).
- `standkit_agent` — только `stdlib` (`http.server`, `subprocess`, `socket`,
  `urllib`), потому что стенды BPMSoft на .NET штатно живут и под Linux, а
  агент должен разворачиваться на голом хосте без сборки колёс под
  конкретную ОС/архитектуру.
- Деплой агента как службы ОС — раздельные шаблоны:
  `standkit_agent/deploy/standkit-agent.service` (systemd, Linux) и
  `standkit_agent/deploy/windows-service.md` (заметки NSSM/Task
  Scheduler/pywin32, Windows).

## Границы free (MIT) / paid

`standkit` — воронка на платный продукт **BPMkit**. Разделительная линия
проводится по ЦЕННОСТИ, а не по расположению кода: транспорт канала обновлений
живёт здесь и лицензируется MIT, но без лицензии и содержимого издателя не даёт
ничего (см. [ADR-0005](adr/0005-companion-transport-in-mit-core.md)).

| В standkit (MIT, бесплатно)                        | В BPMkit (платно, у издателя)                      |
|-----------------------------------------------------|-----------------------------------------------------|
| start/stop/restart headless-процесса стенда          | Провижининг нового стенда "с нуля" (`provision_stand`) |
| Health-пробы: процесс/HTTP/TCP-порт БД и Redis        | Глубокие БД-операции (`db_create/restore/backup`)     |
| Tail/follow лог-файла                                | Деплой пакетов (WSC/UBS), кастомизация JS/C#          |
| Реестр стендов (чтение/запись `projects.json`)        | Генерация документов, git-онбординг пакетов стенда    |
| Secret-first доступ к секретам (обёртка над keyring)  | Административные операции над живым стендом (ESQ, роли, права) |
| **Транспорт канала обновлений** (`standkit_companion`): HTTP-клиент, планировщик, проверка целостности и подписи, раскладка файлов, откат | **Лицензия** (выпуск конвертов, приватный ключ подписи лицензий), **содержимое паттернов**, **подписанные бинари MCP** и ключ подписи артефактов, бэкенд `/v1/content/*` |

Что это значит на практике: пакет канала можно прочитать, собрать и запустить —
но без лицензионного конверта он честно бездействует (`402`/`no_license`), а
конверт резолвится не им, а CLI самого MCP.

`standkit.registry.Registry.add_existing()` — это **привязка уже
существующего стенда** к реестру standkit, не провижининг: каталог/БД/
дистрибутив должны существовать заранее. Полноценный провижининг —
исключительно зона BPMkit.

## Канал обновлений издателя (`standkit_companion`)

Пакет — **транспорт** доставки от бэкенда издателя BPMkit к машине оператора.
Он не знает предмета: ему всё равно, какой markdown приехал и что внутри
бинаря. Решение о том, почему он лежит в MIT-ядре, разбор альтернатив
(приватный репозиторий, `entry points`, флаг в конфиге) и закрытый список «чего
модуль не делает никогда» — [ADR-0005](adr/0005-companion-transport-in-mit-core.md).

### Место в общей схеме

```
   машина оператора                                        издатель
 +-----------------------------------------+          +-----------------+
 |  standkit_hub (процесс)                  |          | бэкенд BPMkit   |
 |    HubHTTPServer.__init__                |  HTTPS   |  /v1/content/   |
 |      +- StatusPoller  (стенды)           |  <-----> |   patterns/sync |
 |      +- CompanionRunner (канал)  --------+----------+   releases/...  |
 |    Handler:  /api/companion/*            |          |   revocations   |
 +--------+--------------------------------+          +-----------------+
          |  мягкий импорт (try/except ImportError)
          v
 +-----------------------------------------+
 |  standkit_companion                      |
 |    runner    — планировщик 3 циклов      |
 |    backend   — единственный выход в сеть |
 |    patterns / releases / revocations     |
 |    signature + ed25519 — проверка подписи|
 |    state + fsutil — состояние, атомарная |
 |                     запись, бэкапы       |
 |    context   — запрос лицензии у CLI MCP |
 +--------+--------------------------------+
          |  run_console: bpmkit setup companion-context --json
          v
 +-----------------------------------------+
 |  CLI клиентского MCP BPMkit              |
 |  (конверт, backend_url, версия, пути)    |
 +-----------------------------------------+
```

Пакет зависит от ядра ровно в двух точках: `standkit.registry.bpmkit_config_dir`
(куда класть состояние) и `standkit.platform.run_console` (как запускать чужой
CLI). Прямой `subprocess.run` запрещён тем же тестом `tests/test_no_window.py`,
что и в остальных пакетах: фоновый поток без своей консоли иначе мигал бы
чёрным окном на Windows.

### Три цикла — три политики

Политика продиктована ценой ошибки, а не единообразием:

```
 цикл          предмет                 проверка                    дефолт
 ------------  ----------------------  --------------------------  ------------
 patterns      markdown паттернов      целостность:                вкл., 30 мин
                                       sha256 записи +             (мин. 5 мин)
                                       bundle_sha256 страницы;
                                       подпись — опция
                                       require_pattern_signature
 releases      исполняемый бинарь MCP  подпись FAIL-CLOSED,        ВЫКЛ., 1 сут
                                       без флага отключения:       (мин. 1 час)
                                       нет сайдкара / signed:false /
                                       не сошёлся sha256 / нет
                                       публичного ключа => НЕ
                                       применяем, старую версию
                                       не трогаем
 revocations   список отзыва лицензий  подпись ОБЯЗАТЕЛЬНА;        вкл., 30 мин
                                       запрос БЕЗ конверта,        (мин. 5 мин)
                                       эндпоинт публичный
```

Почему именно так:

- **паттерны** — текст, не исполняемый код. `bundle_sha256` считается по тому
  же массиву, что и приехал, поэтому ловит порчу в канале, но не подмену; это
  целостность, и подписью она нигде не называется. Механизма подписи markdown у
  издателя ещё нет, поэтому дефолт строгого режима — «не требовать»;
- **бинарь** — скачанный код будет исполнен. Ни в `CompanionSettings`, ни в CLI,
  ни в `/api/companion/*` нет и не должно появиться `skip_signature`/`force`.
  Публичный ключ берётся из ПОСТАВКИ (`ctx.artifact_pubkey`), а не из канала:
  кто подменил бинарь, подменит и ключ рядом с ним. Подписан не файл, а его
  32-байтовый sha256-дайджест — релиз весит десятки мегабайт, а сумма уже
  посчитана для проверки целостности. Занятость целевого файла работающим
  MCP-сервером `apply_staged` выясняет ДО бэкапа и до любой мутации (GAP-161),
  двумя проверками подряд — сначала `mcp_mutex.server_mutex_exists()` (Windows;
  сервер сам объявляет о себе именованным мьютексом `BPMkitMcpServer`, тем же
  именем и по тому же контракту, что `SERVER_MUTEX_NAME` в `bpmkit/core.py`
  поставки BPMkit, GAP-155б — импорт между репозиториями невозможен, поэтому
  константа продублирована с явным комментарием-контрактом), затем, если
  мьютекс не виден, неразрушающая `fsutil.probe_writable()`. Обе — fail-fast
  дополнение к `replace_with_retry`, а не замена его собственной обработки
  `OSError`: занятый файл, не пойманный ни одной из проверок, всё равно ловится
  на самой подмене, тем же `kind="local_io"`;
- **отзыв** — единственный адресат этого файла (клиент с отозванной лицензией)
  по определению не проходит аутентификацию: основной канал отвечает ему
  `401 revoked`. Поэтому эндпоинт публичный и запрос уходит `authorized=False`,
  а подделка документа означала бы СНЯТИЕ отзыва — отсюда обязательная подпись
  и запись на диск БАЙТ В БАЙТ (пере-сериализация JSON сломала бы подпись,
  которую проверяет уже сам MCP).

Порядок одного пробуждения — `revocations` → `patterns` → `releases`
(`runner.RUN_ORDER`): если лицензия отозвана, честнее показать настоящую
причину сразу, чем два невнятных отказа перед ней.

### Где лежит состояние и файлы

| Что | Где | Почему там |
|---|---|---|
| Настройки канала | секция `companion` в `standkit-hub.json` | у канала и UI один источник правды; раздвоение даёт «в интерфейсе одно, в службе другое» |
| Состояние | `companion-state.json` рядом с конфигом (`bpmkit_config_dir()`) | пишется атомарно (`fsutil.atomic_write_text`); битый JSON сбросил бы курсор и вызвал перекачку базы паттернов с нуля |
| Паттерны из канала | пользовательский override-корень (его называет сам MCP), файлы `dev/patterns_<область>_updates.md` + управляемый блок в `dev/patterns_index.md` | читатель паттернов берёт ОДИН корень и не сливает два, поэтому первое применение копирует поставочное дерево целиком (`seed_override_root`); в поставочные файлы канал не дописывает никогда |
| Скачанный релиз | `<config_dir>/companion/staging/` | не `Program Files`: канал обязан работать без прав администратора |
| Резервные копии бинаря | `<config_dir>/companion/backups/` | источник для `rollback`; подрезка истории и удаление файлов разведены (`state.push_history` vs `releases.prune_backups`) |

Ключевое проектное решение состояния: **файлы паттернов — проекция состояния, а
не наоборот**. `patterns.applied` хранит полные записи, а markdown рендерится из
них целиком при каждом применении. Поэтому отзыв паттерна — это удаление записи
плюс перерисовка, а не хирургия по чужому markdown, которая ломается на любом
нестандартном оформлении тела. Лицензионный конверт в состояние не попадает
никогда.

### Как канал взаимодействует с хабом

- **мягкий импорт.** `standkit_hub/server.py` импортирует пакет в
  `try/except ImportError`; `companion_available()` спрашивает
  `standkit_companion.is_available()`. Отсюда `companion_edition()` →
  `edition` в `/api/version` («companion» / «free»);
- **раннер в конструкторе сервера.** `HubHTTPServer.__init__` поднимает
  `CompanionRunner` до `StatusPoller` и при ДВУХ условиях сразу: пакет есть и
  главный рубильник `companion.enabled` включён. Отказ старта канала не роняет
  хаб — текст оседает в `server.companion_error` и уходит в статус вкладки.
  `server_close()` гасит канал вместе с поллером, до закрытия сокета;
- **маршруты.** `GET /api/companion/status` (выключенный канал — тоже `200`:
  UI обязан показать, ПОЧЕМУ ничего не происходит) и шесть действий из
  `COMPANION_ACTION_ROUTES`: `sync`, `check-update`, `stage-update`,
  `apply-update`, `rollback`, `revocations`. В свободной редакции — `503` с
  `edition: "free"` (не `404`: адрес существует и заработает после установки);
  при выключенном рубильнике — `409`. Типизированный `CompanionError`
  раскладывается по кодам таблицей `COMPANION_ERROR_STATUS`: `402` — нужна
  лицензия, `503` — нет CLI BPMkit, `409` — конфликт с состоянием, `502` —
  отказ на стороне канала/бэкенда;
- **ядро не знает логики канала.** Ни лицензии, ни подписей, ни сети в
  `standkit_hub` нет: только «есть ли пакет», «дай статус» и «выполни одно из
  шести действий».

### Как канал взаимодействует с MCP

Ровно одним вызовом и только за лицензионным контекстом:

```
context.resolve()
  -> run_console([<mcp_cli>, "setup", "companion-context", "--json"])
  -> LicenseContext(envelope, license_status, backend_url, mcp_version,
                    package_root, shipped/override_patterns_root,
                    revocations_target, artifact_pubkey, binary_path, ...)
```

Своей копии лицензионной логики канал не заводит: она уже есть в клиентском MCP
и на бэкенде издателя, а третья копия расходится с ними гарантированно. Ответ
кэшируется в памяти на `cache_ttl` секунд (тик трёх циклов иначе запускал бы
процесс трижды) и на диск не попадает никогда — в нём конверт.
`LicenseContext.__repr__` переопределён так, чтобы конверт не утёк в отладочный
вывод, `assert` или трассировку.

Два отказа разведены намеренно, потому что чинятся по-разному: **нет CLI рядом**
(`ContextUnavailable`, `503`, чинит человек полем `companion.mcp_cli`) и **нет
лицензии** (`ChannelError(kind="no_license")`, `402`, чинится у издателя).

### Рубильник для тестов

`STANDKIT_COMPANION_DISABLED` (`runner.DISABLE_ENV`) запрещает старт фонового
потока. Корневой `conftest.py` выставляет её через `setdefault` на весь прогон:
цикл паттернов включён по умолчанию, а хаб поднимает планировщик в конструкторе,
поэтому на машине с живой лицензией каждый из сотни `tests/test_hub_*.py` иначе
заводил бы настоящий фоновый поток и при неудачном жребии разброса реально ушёл
бы в сеть посреди `pytest`. `setdefault`, а не присваивание, — чтобы не
перебивать разработчика, поднявшего переменную осознанно.

## Что уже реализовано в каркасе vs TODO

> Полный, поддерживаемый список «упомянуто в коде, но не реализовано» со ссылками
> на конкретные символы/файлы — [BACKLOG.md](BACKLOG.md). Дорожная карта —
> [ROADMAP.md](ROADMAP.md).

Рабочая минимальная логика, покрытая тестами: `standkit/models.py`,
`standkit/registry.py`, `standkit/health.py` (быстрые пробы: `tcp_open`,
`http_ok`, `process_alive`). Скелетные модули с явными `TODO` в докстрингах:
`standkit/lifecycle.py` (нет graceful stop с эскалацией SIGKILL/таймаутом),
`standkit/platform.py` (нет Job Object на Windows, нет double-fork на Linux),
`standkit/health.py::db_deep_check/redis_deep_check` (заглушки — требуют
опциональных зависимостей `psycopg2`/`pyodbc`/`redis-py`), `standkit_hub`
(опрос стендов — по кнопке "Обновить"/интервалу polling из фронтенда, а не
push/SSE; live follow лога — TODO, сейчас только периодический tail).

`standkit_agent` прошёл прод-харденинг (см. `standkit_agent/security.py`,
`standkit_agent/audit.py`, README.md → раздел «Безопасность»): TLS/mTLS,
fail-closed bind-defaults (loopback-only без явного `--insecure`), скоупы
control/readonly с `hmac.compare_digest`, rate limiting/lockout по IP,
