# Бэклог standkit / BPMkitStand

Честный список того, что **упомянуто в коде, но ещё не реализовано / не
настроено** (каркас, заглушки, зарезервированные значения), с точной ссылкой на
место в коде. Цель — чтобы пользователь пакета и разработчик не принимали
«задел» за готовую фичу.

Метка **[упомянут в коде]** = в коде есть символ/ветка/поле, но реального
поведения за ним нет (или оно возвращает заглушку).

Порядок дорожной карты — см. [ROADMAP.md](ROADMAP.md). Остаточная безопасность
агента — `SECURITY.md` §6. Отдельный список **гэпов** (код работает как задумано,
но сценарий оператора всё равно ломается: настройка недоступна, отказ не объяснён,
рецепт не описан) — [GAPs/](GAPs/README.md).

## Транспорты подключения к стенду

| Пункт | Статус | Упомянут в коде |
|------|--------|-----------------|
| Транспорт **`ssh`** | зарезервирован в enum, реализации нет → `NotImplementedError` | `standkit/models.py::Transport.SSH` («задел на будущее»); фолбэк-`raise` в `standkit_hub/client.py::FederatedClient.status/_dispatch_action/logs` |
| Транспорт **`winrm`** | то же | `standkit/models.py::Transport.WINRM`; там же в `client.py` |

Рабочие транспорты — только `local` и `agent` (оба реализованы; в UI регистрации
предлагаются только они). `ssh`/`winrm` достижимы лишь ручной правкой
`projects.json` и упадут с `NotImplementedError`.

## Health-пробы

| Пункт | Статус | Упомянут в коде |
|------|--------|-----------------|
| Глубокая проба БД (`SELECT 1` через psycopg2/pyodbc) | заглушка, всегда `SKIPPED`; флаг `deep_db` из хаба не передаётся | `standkit/health.py::db_deep_check`, параметр `check_stand(deep_db=…)` |
| Глубокая проба Redis (`PING` через redis-py) | заглушка, всегда `SKIPPED` | `standkit/health.py::redis_deep_check`, `check_stand(deep_redis=…)` |
| `stand_scheme` / `verify_tls` в форме регистрации дашборда | поля есть в реестре и в пробе, но форма регистрации построена по фиксированному белому списку полей — задать схему можно только правкой `projects.json`. Разобрано в [GAP-001](GAPs/GAP-001-registry-fields-out-of-hub-form.md) | `standkit_hub/server.py::_REGISTER_ALLOWED_FIELDS`, `standkit_hub/web/app.js::_REGISTER_FIELD_NAMES` |
| Причина отказа HTTP-пробы | `down` возвращается без текста: «порт закрыт», «TLS-ошибка» и «таймаут» неразличимы в дашборде (у пробы процесса аналог есть — `details['process_reason']`). См. [GAP-002](GAPs/GAP-002-http-probe-down-not-explained.md) | `standkit/health.py::_probe_http`, `http_ok` |
| Адрес Redis (`redis_host` / `redis_port`) | не поля модели, а нетипизированные ключи `Stand.extra`; в форме регистрации и `projects.sample.json` их нет, «не настроено» неотличимо от «не поддержано». См. [GAP-003](GAPs/GAP-003-redis-endpoint-in-extra.md) | `standkit/health.py::_probe_redis`, `standkit/models.py::Stand.extra` |
| Имя каталога логов | зашито строкой `"logs"`; на Linux каталог BPMSoft называется `Logs` и не находится (на Windows проходит из-за регистронезависимой ФС). Плюс путь POSIX-стенда собирается `WindowsPath` на хабе. См. [GAP-006](GAPs/GAP-006-log-dir-case-and-separator.md) | `standkit_hub/logs_browser.py::raw_logs_path`, `standkit/hosting.py::IisBackend.read_logs` |
| `last_deploy` (состояние последнего деплоя) | всегда `UNKNOWN`, источник данных не определён, в UI не выводится | `standkit/health.py::check_stand` (комментарий `last_deploy`), `standkit/models.py::StandStatus.last_deploy` |

Рабочие пробы (без заглушек): процесс (pid/бэкенд), HTTP, БД/Redis по **открытому
TCP-порту** — их достаточно для дашборда.

## Жизненный цикл (kestrel)

| Пункт | Статус | Упомянут в коде |
|------|--------|-----------------|
| Polling готовности веб-хоста после `start()` | не реализован (возвращается pid; готовность проверяется отдельно) | `standkit/lifecycle.py` (докстринг модуля) |
| Блокировка pidfile от гонки двух `start()` | не реализована | там же |
| Восстановление «потерянного» pidfile | **реализовано** — поиск владельца порта, валидация (порт + allowlist образа + рабочий каталог внутри `stand_dir`) и усыновление с подтверждением | `standkit/adopt.py`, `standkit/lifecycle.py::adopt` |
| Доп. окружение процесса (`ASPNETCORE_ENVIRONMENT` и т.п.) | «зона расширения следующей итерации» | `standkit/lifecycle.py::_kestrel_start` |
| Graceful stop (SIGTERM→таймаут→SIGKILL / CTRL_BREAK_EVENT) | **реализовано** — эскалация мягко → таймаут → жёстко | `standkit/platform.py::stop` |
| Рабочий каталог процесса для WOW64 (32-битный стенд под 64-битным Python) | не реализовано — усыновление таких процессов даёт честный отказ | `standkit/adopt.py::_windows_process_cwd` |
| Windows Job Object / Linux double-fork | упрощённо (CREATE_NO_WINDOW / setsid) | `standkit/platform.py` (докстринг модуля) |

## Хаб / клиент

| Пункт | Статус | Упомянут в коде |
|------|--------|-----------------|
| Параллельный опрос агентов | **реализовано** — `ThreadPoolExecutor`, порядок результатов сохраняет порядок реестра | `standkit_hub/client.py::FederatedClient.status_all` |
| Кэш/дебаунс частых опросов | **реализовано** — фоновый поллер держит снапшот состояния, конфиг и реестр кэшируются по отпечатку файла | `standkit_hub/poller.py`, `standkit_hub/server.py::build_snapshot` |
| CLI регистрации стенда (`standkit register …`) | не реализовано: запись в реестр возможна только из UI (`POST /api/stand/register`), правкой `projects.json` руками или `Registry.add_existing()` из Python. На headless-хосте агента UI недоступен (хаб слушает loopback) — обходной рецепт живёт в кукбуке | `standkit/registry.py::Registry.add_existing`, `standkit_hub/server.py` (маршрут регистрации) |
| Ярлык на рабочем столе для **macOS** | осознанно не реализовано — возвращается понятный статус | `standkit_hub/shortcut.py` (докстринг) |
| Нативный трей (иконка со сводным состоянием, баллоны при падении) | не реализовано — потребовало бы `pystray`/`Pillow` против инварианта stdlib-only. Вместо него PWA-установка и компактный режим `?view=compact` | `standkit_hub/web/manifest.webmanifest` |
| Автозапуск хаба при входе в систему | не реализовано; механика ярлыка есть | `standkit_hub/shortcut.py` |
| Остановка хаба, когда дашборд никто не смотрит (idle-shutdown / heartbeat от фронта) | не реализовано — запущенный ярлыком процесс живёт под `pythonw` без окна до перезагрузки или ручного снятия. Дубли при повторном клике по ярлыку закрыты single-instance проверкой, но сам «вечный» процесс остаётся | `standkit_hub/__main__.py` (`serve_forever` без таймаута), `standkit_hub/server.py::probe_hub_instance` |
| Остановка хаба из интерфейса (кнопка «Завершить работу диспетчера») | не реализовано — единственный штатный способ Ctrl+C недоступен при запуске ярлыком (консоли нет) | `standkit_hub/__main__.py` (обработка `KeyboardInterrupt`) |

|------|--------|-----------------|

## Приёмка

| Пункт | Статус |
|------|--------|
| **Агент на Linux** | **первая живая установка 18.08.2026** — Ubuntu 24.04 (`BPM-docker-test`), стенд `survey9` в Docker: установка через pipx, регистрация стенда из Python (`Registry.add_existing`), секреты через `STANDKIT_SECRET__*`, служба systemd, проверка API токеном. Вскрыла: жёсткую схему `http://` в HTTP-пробе (строка выше), отсутствие CLI регистрации (строка выше) и набор типовых ошибок оператора (PEP 668, забытый префикс секрета, владелец `agent.env`, `stand_host=0.0.0.0`, чтение реестра только при старте) — всё разобрано в кукбуке |
| **Docker** бэкенд (одиночный контейнер + compose) | **живая приёмка проведена 17.08.2026** на Docker Engine 29.6.1: 50 проверок основного цикла (start/stop/restart по фактическому `State.StartedAt`, логи, health, идемпотентность, негативы, работа без `docker` в PATH) + 6 проверок граничных состояний (paused, crash-loop, exited, подстрочные имена сервисов, кириллица в логах). Вскрыла два ложных «стенд жив» — исправлены в этой же ветке (см. CHANGELOG) |
| **k8s** бэкенд | **живая приёмка проведена 17.08.2026** на кластере k3s 1.30 (k3d): 28 проверок — scale/rollout restart с проверкой пересоздания подов, `readyReplicas`, `k8s_replicas`, логи, NodePort-проба, негативы по деплойменту/namespace/контексту/PATH. Вскрыла ложное «жив» при нуле реплик — исправлено |
| **IIS** бэкенд | **живая приёмка проведена 17.08.2026** на настоящем стенде BPMSoft 1.9.1.2 (.NET Framework + PostgreSQL) в IIS 10 / .NET Framework 4.8: сайт `iis19` (порт 5081) + вложенное приложение `/0` + сайт-сосед на ТОМ ЖЕ пуле; 66 живых проверок (окружение и автодетект 13, жизненный цикл site-scoped 17, `w3wp` 7, логи 4, отсутствие elevation 10 + 4 кросс-платформенных, ручки хаба 6, граничные состояния канала управления 5). Вскрыла 4 дефекта (пул при автодетекте, `state:Unknown`, ложный диагноз «нет прав», логи в подпапках-датах) — исправлены в этой же ветке, см. CHANGELOG |
| Контур для повторной приёмки k8s | на Windows с **cgroup v1** (проверить: `docker info --format {{.CgroupVersion}}`) Kubernetes ≥1.32 не поднимается — `kind` с `kindest/node:v1.36.1` падает на `kubeadm init`, k3s 1.35 не доходит до CoreDNS. Рабочий вариант — k3d с `--image rancher/k3s:v1.30.6-k3s1`; после создания кластера поправить kubeconfig: k3d прописывает `host.docker.internal`, нужен `kubectl config set-cluster <ctx> --server=https://127.0.0.1:<порт из docker port k3d-<cluster>-serverlb>` |

### Остатки после приёмки 17.08.2026 — закрыты в тот же день

| Пункт | Как закрыт |
|------|--------|
| Контейнер в crash-loop | `describe_state` объясняет состояние словами: «контейнер в цикле перезапуска (перезапусков: N)», а у контейнера, пойманного в running-фазе, — «уже перезапускался N раз, возможен цикл падений». Причина уходит в `StandStatus.details['process_reason']`, поэтому витрина показывает диагноз вместо мигающего индикатора. Сам вердикт по-прежнему отражает мгновенное состояние — это честно, контейнер и правда попеременно жив |
| Контракт `read_logs` при отсутствующем CLI | оба бэкенда возвращают `None`; контракт зафиксирован в докстринге протокола `HostingBackend` |
| `KubernetesBackend.stop` | бросает `HostingError` с текстом kubectl, как `DockerBackend.stop` |
| `read_logs` при нескольких репликах (k8s) | чтение по label-селектору (`logs -l ... --prefix`) со всех подов. Отдельно: общий вывод НЕ обрезается хвостом до `n` — `--tail` уже применён kubectl к каждому поду, а хвост принадлежит поду, писавшему последним |
| `restart` (k8s) не ждёт готовности | после `rollout restart` выполняется `rollout status` (`K8S_ROLLOUT_WAIT_SEC`, по умолчанию 60 с; `0` возвращает прежнее поведение) |

### Открытые остатки

| Пункт | Статус |
|------|--------|
| Признак «краш-луп» в самом вердикте | сейчас различить «стенд работает» и «стенд поднялся на секунду между падениями» можно только по тексту `reason`. Возможный шаг — отдельное состояние в витрине (жёлтый вместо зелёного) при `restart_count > 0` и свежем `StartedAt` |
| Живая приёмка на нескольких узлах | всё проверено на одноузловом кластере: поведение при подах, разъехавшихся по узлам, и при `NodePort` за внешним балансировщиком не проверялось |
| Усыновление стенда (kestrel) | **живая приёмка проведена** на реальном стенде, поднятом мимо диспетчера: поиск владельца порта, признание своего стенда и отказ для чужого, отсутствие действий без подтверждения, остановка по подтверждению, протухший pidfile. Именно она вскрыла, что на Windows рабочий каталог процесса приходится читать из PEB — путь к стенду не встречается ни в `ExecutablePath`, ни в командной строке |
| Усыновление стенда (IIS) | **проверено живьём 17.08.2026**: автоопределение сайта по physical path и по биндингу (в т.ч. `%SystemDrive%`-путь и игнор `net.tcp`-биндинга), снятие `w3wp` по пулу с проверкой, что соседний пул не тронут, различение «сайт остановлен / пул остановлен / порт держит http.sys / состояние не выяснено». Именно она вскрыла, что пул при автодетекте не заполнялся (атрибут `APPPOOL.NAME`) |
| Контур для повторной приёмки IIS | на этом хосте **служба WAS падает** (System log: «Служба активации Windows была неожиданно завершена», W3SVC уходит с кодом 1067) при сценарии «создать новый App Pool + сайт и сразу дать запрос» — воспроизведено 3/3, в т.ч. с отдельным физическим каталогом. Лечится `iisreset /restart` (либо `sc start WAS` + `sc start W3SVC`). Проверки, которым нужен ВТОРОЙ пул, поэтому переиспользуют существующие пул и сайт (`set app <site>/ /applicationPool:DefaultAppPool`), а не создают новые. Побочно этот же контур дал живые примеры транзиентных RPC-сбоев `appcmd` |
