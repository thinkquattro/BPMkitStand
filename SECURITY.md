# SECURITY — модель безопасности standkit-агента

> Аудитория: инженеры и self-hosted администраторы, разворачивающие
> `standkit_agent` на хостах стендов. Клиентский (заказчицкий) документ по
> модели удалённой работы готовится отдельно на основе этого файла.
> Статус кода: прод-харденинг выполнен (v0.2 агента), см. чек-лист и
> остаточные пункты ниже.

## 1. Что защищаем (assets) и почему это критично

`standkit_agent` — headless-демон на хосте стенда, который по HTTP(S) умеет
**запускать, останавливать и перезапускать процессы стенда** и читать его
логи. То есть агент по своей природе — **поверхность удалённого исполнения
кода (RCE)**: тот, кто получит контроль-доступ к агенту, управляет жизненным
циклом процессов на хосте. Поэтому к нему применяется модель угроз как к
элементу управляющего контура (management plane), а не как к обычному
прикладному API.

Активы: (1) контроль над процессами стенда; (2) содержимое логов стенда;
(3) сам хост (через возможность запускать процессы). Агент НЕ хранит секретов
клиента и НЕ содержит контента платформы — только оркестрацию.

## 2. Противники и границы доверия

- **Сетевой злоумышленник** (тот же сегмент/периметр): перехват трафика,
  попытка подключиться к порту агента, brute-force токена.
- **Утечка токена** (лог, история команд, скриншот): попытка использовать
  украденный Bearer-токен.
- **Инсайдер с доступом к сети управления**: злоупотребление легитимным
  доступом — здесь работает аудит.

Граница доверия: агент доверяет только клиентам, прошедшим (а) TLS/mTLS-
транспорт и (б) аутентификацию по скоупу. Всё остальное — недоверенное.

## 3. Модель развёртывания (как разворачивать безопасно)

Рекомендуемые топологии (в порядке предпочтения):

1. **Loopback + управляющий контур.** Агент слушает `127.0.0.1`, доступ к
   нему — только через SSH-туннель / WireGuard / VPN до хоста. Наружу порт
   агента не публикуется вообще. Самый простой безопасный вариант — дефолт.
2. **mTLS за firewall.** Агент слушает управляющий интерфейс с TLS +
   обязательным клиентским сертификатом (`--tls-client-ca`). Подключиться
   может только держатель сертификата, подписанного доверенным CA (например,
   Companion оператора). Источники ограничены firewall-allowlist.

**Категорически нельзя:** публиковать порт агента в интернет; выставлять его в
недоверенную сеть открытым HTTP; запускать под root/LocalSystem; хранить токен
в открытых конфигах/истории команд.

## 4. Secure-defaults, действующие в коде (v0.2)

- **Bind по умолчанию `127.0.0.1`** (не `0.0.0.0`).
- **Fail-closed**: non-loopback host без TLS → агент **не стартует**
  (`InsecureBindError`) ещё до открытия сокета. Обход — только явный
  `--insecure` (dev/loopback) с громким предупреждением в stderr.
- **TLS**: `PROTOCOL_TLS_SERVER`, минимум **TLS 1.2**, консервативный набор
  AEAD/ECDHE-шифров (forward secrecy), выключено сжатие (CRIME).
- **mTLS**: `--tls-client-ca` → `CERT_REQUIRED`; клиент без валидного
  сертификата отсекается на TLS-хендшейке, до обработчика. CN — в аудит.
- **AuthN**: Bearer-токен, сравнение только `hmac.compare_digest`
  (анти-timing). **Скоупы**: `control` (start/stop/restart + чтение) и
  `readonly` (только чтение).
- **Lockout**: 5 неудачных аутентификаций с одного IP за 300 c → `429` до
  конца окна (настраивается).
- **Аудит**: append-only JSON-lines (`--audit-log`, дефолт
  `~/.standkit/audit.log`), каждая операция (ok/denied/error) с src_ip,
  идентичностью, действием и кодом. **Токены никогда не пишутся.**
- **Input-hardening**: лимит тела 64 КБ (проверка до чтения), кап `n` логов
  10000, таймаут соединения 30 c, whitelist-валидация имени стенда, `400`
  вместо `500`/креша на некорректный ввод, `405` на PUT/DELETE/PATCH.
- **systemd least-privilege** (`deploy/standkit-agent.service`):
  `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`,
  `PrivateDevices`, `CapabilityBoundingSet=` (пусто), `MemoryDenyWriteExecute`,
  `LockPersonality`, `RestrictNamespaces`, `SystemCallFilter=@system-service`,
  выделенный не-root `User=`/`Group=`, урезанные `ReadWritePaths`.

## 4.1. Усыновление стендов, поднятых вне диспетчера

Диспетчер умеет брать под управление kestrel-стенд, запущенный мимо него
(вручную из консоли, скриптом, чужой сессией): он находит владельца
TCP-порта стенда и, после подтверждения, записывает pidfile, чтобы обычные
Стоп/Рестарт заработали. Это **расширение RCE-поверхности**: появляется путь,
в котором управляющий контур убивает процесс, найденный по номеру порта, а не
запущенный им самим. Поэтому механизм ограничен так:

- **Три обязательных условия валидации** (все сразу, а не любое из них, см.
  `standkit.adopt.validate_candidate`): порт процесса совпадает со
  `stand.stand_port`; имя образа входит в allowlist (`dotnet`,
  `BPMSoft.WebHost`, `w3wp`); рабочий каталог, путь исполняемого файла или
  командная строка указывают **внутрь** `stand.stand_dir`. Не выполнено хотя
  бы одно — усыновления нет, пользователь получает отказ с указанием, какой
  именно процесс занимает порт.
- **Никакого тихого kill.** Без явного согласия `stop`/`restart` бросают
  `AdoptionRequired` с описанием кандидата и не трогают процесс. Согласие
  передаётся отдельным параметром (`?force=1` в хабе, `POST
  /stand/<name>/adopt` у агента) — оно не выводится и не «запоминается».
- **Скоуп и аудит.** У агента `adopt` отнесён к `CONTROL_ACTIONS`: readonly-
  токен усыновлять не может, каждая попытка (ok/denied/error) пишется в
  аудит-лог наравне с start/stop/restart.
- **CSRF и токен хаба.** Эндпоинты усыновления — мутации, поэтому проходят ту
  же проверку сессионного токена и заголовка `Origin`, что и остальные
  мутирующие вызовы (см. `standkit_hub.security`).
- **Протухший pidfile** (процесс из файла уже мёртв) удаляется до эскалации —
  чтобы диспетчер не отправил сигнал по переиспользованному ОС pid.

Остаётся осознанным допущением: процесс, полностью совпавший по всем трём
уликам, считается стендом. Злоумышленник, уже способный запустить `dotnet` из
каталога стенда на этом хосте, находится внутри границы доверия — против него
защищает не эта проверка, а разграничение доступа к хосту.

## 5. Чек-лист развёртывания на прод

- [ ] Агент слушает loopback ИЛИ настроен TLS (лучше mTLS). Порт не в интернет.
- [ ] Отдельный сервис-аккаунт без root; systemd-hardening из unit применён.
- [ ] Токены сгенерированы криптостойко, лежат в secret-store (env/keyring),
      не в открытых конфигах; разные токены на control и readonly.
- [ ] Firewall-allowlist источников (только Companion оператора / сеть
      управления).
- [ ] Аудит-лог пишется на защищённый носитель; настроен внешний сбор/ротация
      (см. остаточные пункты) и мониторинг `denied`/`429`.
- [ ] TLS-сертификаты и приватный ключ — с корректными правами (0600), выданы
      доверенным CA; продумана ротация.
- [ ] Проверено, что `--insecure` НЕ используется на этом хосте.

## 6. Остаточные пункты (осознанные TODO следующих итераций)

Не закрыты в v0.2 и требуют внимания перед массовым прод-развёртыванием:

- **PKI/сертификаты**: агент только потребляет готовые PEM. Выпуск, раздача и
  ротация серверных/клиентских сертификатов — пока забота оператора. Нужен
  задокументированный процесс (или интеграция с внутренним CA).
- **Ротация токенов «на лету»** без рестарта агента — не реализована.
- **Per-stand ACL**: control-скоуп управляет всеми стендами реестра агента;
  разбивки «токен/CN → конкретный стенд» нет.
- **CN→scope маппинг** для mTLS: сейчас скоуп всегда определяется Bearer-
  токеном, CN сертификата — только для аудита.
- **Ротация/размерный кап аудита**: до-аутентификационные ответы (`404`/`405`)
  и поток `denied` могут наливать файл; нужна ротация (logrotate/размерный
  лимит) и защита от переполнения диска.
- **Кап числа потоков**: `ThreadingHTTPServer` не ограничивает число
  одновременных обработчиков — при флуде соединений возможно исчерпание
  ресурсов. Нужен bounded thread pool / лимит соединений (плюс внешний
  rate-limit на reverse-proxy).
- **`Transfer-Encoding: chunked`**: лимит тела опирается на `Content-Length`;
  chunked-запрос лимит не учитывает. Явно отклонять chunked или считать длину.
- **Windows-служба**: обёртка через `sc.exe`/pywin32 с least-privilege — не
  входила в объём v0.2 (есть заметки в `deploy/windows-service.md`).
