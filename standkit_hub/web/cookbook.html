BPMkitStand — кукбук

v0.6.1

Что это и зачем

BPMkitStand — бесплатный (MIT) диспетчер стендов BPMSoft. Локальная веб-страница, с которой видно все ваши стенды и можно их запускать, останавливать, перезапускать, смотреть логи и чистить Redis — без PowerShell и без «а какой там был порт».

Аналитику аналитик

Свой стенд поднимается и гасится кнопкой. Видно, живой ли он, отвечает ли БД, и что пишет в лог, когда «всё сломалось».

Разработчику разработчик

Пять-десять стендов в одном списке, честный старт (спиннер до реального ответа web-хоста), усыновление процессов, поднятых мимо диспетчера, IIS/Docker/k8s, удалённые хосты через агента.

Границы инструмента BPMkitStand управляет уже существующими стендами. Развернуть стенд с нуля, накатить пакет, поправить схему — это платный BPMkit / Companion. Кнопка «Зарегистрировать стенд» — это привязка существующего стенда к реестру, а не провижининг.

Установка за 3 шага

Нужен только Python 3.10+. Сторонних зависимостей у ядра нет вообще.

  1. Поставить пакет

    pip install standkit
    pip install "git+https://github.com/thinkquattro/BPMkitStand.git"
    git clone https://github.com/thinkquattro/BPMkitStand.git
cd BPMkitStand
pip install -e ".[dev]"
python -m pytest -q

  2. Запустить дашборд

    standkit-hub

    Откроется браузер на http://127.0.0.1:8770. Дашборд слушает только loopback — из сети к нему не подключиться, это by design.

    Нативное окно вместо вкладки браузера (опционально):

    pip install "standkit[desktop]"
standkit-hub --desktop

  3. Добавить стенды

    Кнопка «Зарегистрировать стенд» над таблицей — заполняете имя, каталог, порт, параметры БД. Либо правите реестр руками — см. Реестр стендов.

Ярлык на рабочий стол аналитик

Вкладка «Настройки» → создать ярлык. Ярлык стартует хаб через pythonw.exe — без чёрного окна консоли. Повторный клик по ярлыку не поднимает второй диспетчер: если он уже работает, просто откроется браузер на нём (исправлено в 0.6.1).

PWA и компактный режим Chrome и Edge предложат «Установить приложение» — дашборд получит своё окно без адресной строки и иконку в панели задач. Компактный режим-виджет включается кнопкой ▭ в шапке (или адресом ?view=compact): остаются только имена стендов, состояние и старт/стоп — очистка Redis и колонка «Транспорт» намеренно скрыты, по такому окну кликают мимоходом.

Как остановить диспетчер

Отдельной команды «стоп» у хаба нет — и не будет: это обычный процесс, а не служба.

  • Запущен из консоли — Ctrl+C в том же окне. Диспетчер печатает [standkit-hub] остановлено (Ctrl+C) — это штатный выход, а не падение.
  • Запущен ярлыком — окна нет, процесс живёт под pythonw.exe. Закрыть вкладку браузера недостаточно: idle-shutdown у хаба нет, он продолжит работать. Снимите процесс через диспетчер задач или: 
    « Windows »
taskkill /IM pythonw.exe /F

« Linux »
pkill -f standkit_hub
  • Режим --desktop — закрытие нативного окна останавливает и сервер.
Остановка диспетчера не трогает сами стенды — они продолжают работать. И наоборот: пока диспетчер выключен, открытая вкладка покажет баннер «нет связи».

Что делать, когда дашборд «завис»

Диспетчер живёт отдельным процессом и может быть остановлен или пережить перезагрузку. Начиная с 0.6.1 вкладка это честно показывает: сверху появляется баннер «нет связи», устаревшая таблица гасится. Лечится повторным запуском standkit-hub (или ярлыком).

Тема, компактный режим, «О программе»

Реестр стендов разработчик

Реестр — один JSON-файл, общий с MCP BPMkit. Стенды лежат под ключом projects.

Где он лежит

Путь резолвится по порядку, первый сработавший выигрывает:

  1. переменная окружения BPMSOFT_PROJECTS_FILE;
  2. %APPDATA%\BPMkit\projects.json (Windows) / ~/.config/BPMkit/projects.json (Linux);
  3. ./projects.json в текущем каталоге.

Минимальная запись (kestrel)

{
  "default": "",
  "projects": {
    "demo9": {
      "transport": "local",
      "host_kind": "kestrel",
      "stand_dir":  "C:\\BPMSoft\\demo9",
      "stand_dll":  "BPMSoft.WebHost.dll",
      "dotnet":     "dotnet",
      "stand_host": "127.0.0.1",
      "stand_port": 5030,
      "db_type": "postgres",
      "db_host": "127.0.0.1",
      "db_port": 5432,
      "db_name": "demo9",
      "redis_db": 1,
      "secret_ref_db": "standkit:demo9:db"
    }
  }
}
Secret-first — паролей в реестре нет В projects.json хранятся только ссылки на секреты (secret_ref_db, agent_secret_ref). Значение резолвится в порядке: переменная окружения → keyring → фолбэк. Секрет не пишется в лог и не попадает в текст ошибки. 
pip install "standkit[secrets]"
python -m standkit.secrets set standkit:demo9:db

Полный образец схемы со всеми полями — projects.sample.json в репозитории.

Виды хостинга: kestrel / IIS / Docker / k8s разработчик

Два независимых измерения: transport — где управлять стендом (local / agent), host_kind — как он хостится. Например transport=agent + host_kind=docker — удалённый контейнер.

По умолчанию. Диспетчер сам поднимает dotnet <stand_dll> и держит pidfile. Дополнительных полей не требует. Неизвестное значение host_kind откатывается сюда же.

Только Windows, работа через appcmd.exe.

ПолеОбязательностьНазначение
iis_siteнужно хотя бы одно из двухимя IIS-сайта
iis_app_poolимя Application Pool
iis_stdout_log_dirопциональнопапка stdout-логов ASP.NET Core (иначе <stand_dir>\logs)

«Стенд в IIS» = его Site. Диспетчер намеренно не трогает App Pool: пул может быть общим с другими приложениями, его остановка положила бы и их. Пул задействуется, только если iis_site не задан вовсе.

Рестарт = stop site + start site, без recycle пула. «Жив» определяется состоянием сайта, а не открытым портом: порт держит http.sys даже у остановленного сайта.

"example-iis": {
  "transport": "local",
  "host_kind": "iis",
  "iis_site": "BPMSoft-example-iis",
  "iis_app_pool": "BPMSoft-example-iis-pool",
  "stand_dir": "C:\\inetpub\\wwwroot\\example-iis",
  "stand_host": "127.0.0.1",
  "stand_port": 5000
}
Требует прав администратора См. отдельный разбор ниже: IIS: запуск от имени администратора.

Через kubectl в PATH + доступный kubeconfig с правами get/scale/rollout/logs.

Удалённые стенды и агенты разработчик

Стенды на других хостах — виртуалки, серверы, контуры заказчика — управляются через федерацию лёгких headless-агентов. На хосте стенда живёт standkit_agent, дашборд оператора ходит к нему по HTTPS с Bearer-токеном.

   Машина оператора                      Хосты стендов (Windows / Linux)
 ┌──────────────────────┐             ┌───────────────────────────────┐
 │  standkit_hub        │  HTTPS+токен│  standkit_agent (хост A)      │
 │  веб-дашборд         │────────────▶│  stdlib http.server           │
 │  федеративный клиент │             │  + standkit (то же ядро)      │
 │  локальное ядро      │             │  start/stop/restart/logs      │
 │  + N агентов         │  HTTPS+токен└───────────────────────────────┘
 │                      │────────────▶  standkit_agent (хост N) …
 └──────────────────────┘
Правило №1 Агент по HTTP принимает команды start/stop/restart процессов — это RCE-поверхность по дизайну. Никогда не выставляйте его в недоверенную сеть открытым HTTP. Только TLS с обязательной клиентской аутентификацией (mTLS), либо внутри VPN / SSH-туннеля / управляющего контура.

Что защищает агента из коробки

  • Loopback по умолчанию — --host = 127.0.0.1.
  • Fail-closed — non-loopback host без TLS: агент отказывается стартовать. Обойти можно только явным --insecure (dev, изолированный периметр).
  • TLS 1.2+ с AEAD-шифрами; mTLS (--tls-client-ca) отклоняет соединение без валидного клиентского сертификата ещё на хендшейке.
  • Bearer-токен сравнивается через hmac.compare_digest. Два скоупа: control (управление + чтение) и readonly.
  • Lockout по IP после серии неудач; append-only JSON-аудит без токенов и секретов.

Установка агента — на каждом хосте стенда

  1. Поставить пакет

    pip install standkit

    Тот же пакет, что и у оператора: standkit_agent едет внутри, отдельной установки не требует. Нужен Python 3.10+ и dotnet для запуска самих стендов. Ставить с GitHub (pip install "git+https://…") имеет смысл, только если нужен ещё не выпущенный main.

  2. Положить реестр стендов этого хоста

    Тот же формат, что у дашборда. Важно: на стороне агента стенд остаётся transport: "local" — агент поднимает его у себя локально. Удалённым он становится только в реестре оператора.

    {
  "default": "",
  "projects": {
    "client-uat": {
      "transport": "local",
      "stand_dir": "/opt/bpmsoft/client-uat",
      "stand_dll": "BPMSoft.WebHost.dll",
      "dotnet": "dotnet",
      "stand_host": "0.0.0.0",
      "stand_port": 5000,
      "db_type": "postgres",
      "db_host": "127.0.0.1",
      "db_port": 5432,
      "db_name": "client_uat",
      "secret_ref_db": "standkit:client-uat:db"
    }
  }
}

  3. Задать токены как секреты

    Токен не передаётся в командной строке открытым текстом — только ссылкой на секрет.

    python -c "import secrets;print(secrets.token_urlsafe(32))"

python -m standkit.secrets set standkit:client-uat:agent-token
# опционально — только чтение, для мониторинга без управления:
python -m standkit.secrets set standkit:client-uat:agent-readonly-token

  4. Выпустить сертификаты (для доступа по сети)

    Агент только потребляет готовые PEM — выпуск и ротация остаются задачей вашей PKI. Минимальный самоподписанный вариант для закрытого контура:

    « CN серверного сертификата = имя хоста, по которому к нему ходит дашборд »
openssl req -x509 -newkey rsa:4096 -nodes -days 365 \
    -keyout agent.key -out agent.crt -subj "/CN=client-host"

« CA для клиентских сертификатов (mTLS) »
openssl req -x509 -newkey rsa:4096 -nodes -days 365 \
    -keyout clients-ca.key -out clients-ca.crt -subj "/CN=BPMkitStand clients CA"

  5. Запустить агента

    python -m standkit_agent \
    --registry ./projects.json \
    --token-ref standkit:client-uat:agent-token
    python -m standkit_agent --host 0.0.0.0 --port 8765 \
    --registry /opt/standkit/projects.json \
    --token-ref standkit:client-uat:agent-token \
    --readonly-token-ref standkit:client-uat:agent-readonly-token \
    --tls-cert /etc/standkit/agent.crt \
    --tls-key /etc/standkit/agent.key \
    --tls-client-ca /etc/standkit/clients-ca.crt \
    --audit-log /var/log/standkit/audit.log

    Все параметры — python -m standkit_agent --help.

  6. Оформить как службу

    • Linux (systemd) — готовый least-privilege юнит standkit_agent/deploy/standkit-agent.service.
    • Windows — инструкция standkit_agent/deploy/windows-service.md.

  7. Подключить на стороне оператора

    В projects.json дашборда стенд объявляется удалённым одним полем:

    "client-uat": {
  "transport": "agent",
  "agent_url": "https://client-host:8765",
  "agent_secret_ref": "standkit:client-uat:agent-token",

  "stand_dir": "/opt/bpmsoft/client-uat",
  "stand_port": 5000,
  "db_type": "postgres",
  "db_host": "db-host",
  "db_port": 5432,
  "db_name": "client_uat"
}

    И тот же токен кладётся в секрет у оператора:

    python -m standkit.secrets set standkit:client-uat:agent-token

    После перезапуска дашборда стенд появится в общем списке, в колонке «Транспорт» — agent. Кнопки работают так же, как для локальных.

Проверить агента напрямую

Readonly-токеном — чтобы гарантированно ничего не запустить:

curl --cacert agent.crt \
     --cert client.crt --key client.key \
     -H "Authorization: Bearer <readonly-token>" \
     https://client-host:8765/stands

Чего у агента осознанно ещё нет

  • Полноценная PKI: выпуск и ротация сертификатов — забота оператора.
  • Per-stand ACL: скоуп бинарный, control видит и управляет всеми стендами реестра агента.
  • Ротация токенов на лету без рестарта агента.
  • CN клиентского сертификата → скоуп (сейчас CN только для идентичности в аудите).
  • Параллельный опрос агентов дашбордом — пока последовательный.
  • Транспорты ssh / winrm — схемой допускаются, логика не реализована.

Технические заметки и FAQ

⚠️ IIS: почему нужен запуск «от имени администратора» и как это сделать

Почему. Управление IIS идёт через %windir%\system32\inetsrv\appcmd.exe. Он правит конфигурацию IIS и читает %windir%\system32\inetsrv\config\redirection.config — а это требует прав администратора. Членства в группе IIS_IUSRS недостаточно.

Без elevation любая IIS-операция падает по правам — типично код 1168 или «не удалось открыть файл конфигурации из-за отсутствия необходимых разрешений». Диспетчер в этом случае отдаёт понятную подсказку «запустите от имени администратора» прямо в тексте ошибки, а не молчит.

Как запустить elevated

  • Ярлык или консоль → правый клик → «Запуск от имени администратора», затем standkit-hub.
  • Из уже поднятой административной консоли — просто standkit-hub.
  • Ярлык всегда elevated: правый клик по ярлыку → Свойства → Ярлык → Дополнительно… → галка «Запуск от имени администратора».
  • Из PowerShell: 
    Start-Process powershell -Verb RunAs -ArgumentList '-NoExit','-Command','standkit-hub'
Стендам на kestrel, Docker и k8s права администратора не нужны. Требование касается только host_kind: "iis".
Что значит «усыновить» стенд и бейдж «вне диспетчера»

Проблема. Управление kestrel-стендом завязано на pidfile: диспетчер знает pid только тех стендов, которые сам и запустил. Стенд, поднятый руками (dotnet BPMSoft.WebHost.dll из консоли, скриптом, чужой сессией), виден живым по TCP-порту — но остановить или перезапустить его нечем, pid неизвестен. Такой стенд помечается в таблице бейджем «вне диспетчера».

Усыновление (adoption) — это взятие такого процесса под управление. Диспетчер:

  1. находит владельца порта стенда (Windows: netstat -ano → tasklist → Win32_Process; Linux: ss -ltnp → lsof → разбор /proc);
  2. проверяет, что это действительно процесс ЭТОГО стенда — совпадение порта, имя образа из allowlist (dotnet, bpmsoft.webhost, w3wp) и рабочий каталог внутри stand_dir;
  3. показывает вам, что именно нашёл, и ждёт явного подтверждения.
Без подтверждения процесс не трогается. Найденный по порту процесс никогда не убивается «по факту находки»: без совпадения пути к стенду усыновления не происходит — иначе диспетчер прибил бы чужой процесс, случайно севший на тот же порт.

Как это выглядит. Жмёте ■ или ⟳ на стенде с бейджем «вне диспетчера» — вместо действия появляется диалог «Стенд запущен вне диспетчера» с описанием найденного процесса (pid, образ, путь). Соглашаетесь — команда повторяется уже с усыновлением. Отказываетесь — ничего не происходит.

Порты: 8770 занят / стенд не отвечает на своём порту

8770 — порт дашборда, зафиксирован (от него зависит scope PWA). Если его занял чужой сервис, хаб откатится на свободный порт. Если его занял другой экземпляр хаба — новый не поднимется, откроется браузер на уже работающем.

Порт стенда: колонка HTTP красная, а процесс up — обычно стенд ещё прогревается (первый старт BPMSoft — минуты) либо упал на старте. Смотрите панель логов.

Для IIS открытый порт сам по себе «живым» не считается: http.sys держит порт даже у остановленного сайта — поэтому статус берётся из состояния сайта.

Безопасность дашборда: почему только 127.0.0.1
  • Хаб слушает только loopback — из сети к нему не подключиться.
  • Сессионный токен отдаётся в <meta> при рендере страницы.
  • Мутирующие запросы защищены CSRF-токеном и проверкой заголовка Origin.
  • Статика отдаётся без авторизации (это только вёрстка), API — нет.

Модель угроз и чек-лист развёртывания — SECURITY.md в репозитории.

Кракозябры в выводе внешних команд

Вывод appcmd, netstat, tasklist, docker декодируется цепочкой utf-8 → OEM(cp866) → cp1251 — одной общей реализацией в standkit.hosting. Если вы всё же видите кракозябры в тексте ошибки — это баг, заводите issue с точной командой.

Почему нет зависимостей и нет сборки фронтенда

Осознанный инвариант: standkit, standkit_agent и серверная часть standkit_hub — stdlib-only, dependencies = []. Никаких Flask / FastAPI / requests. Фронтенд — vanilla JS/CSS без сборщика и без CDN, работает офлайн (этот кукбук — тоже).

Опциональные extra ставятся явно и импортируются в try/except ImportError с понятным сообщением:

ExtraЧто даёт
standkit[secrets]keyring как backend хранения секретов
standkit[desktop]pywebview — нативное окно вместо вкладки браузера
standkit[dev]pytest

Причина проста: инструмент ставят на прод-контуры и машины заказчика, где каждая лишняя зависимость — это согласование.

Windows и Linux: что различается

Кроссплатформенность — инвариант: только pathlib.Path, никакого хардкода C:\…, ветки win32 / POSIX разделены явно. Различия по факту:

  • IIS — только Windows.
  • Путь реестра — %APPDATA%\BPMkit\ против ~/.config/BPMkit/.
  • Служба агента — systemd-юнит против инструкции для Windows-службы.
  • Поиск процесса при усыновлении — netstat/tasklist против ss/lsof//proc.
Честные отказы: SKIPPED, NotImplementedError и docs/BACKLOG.md

Принцип проекта: нереализованная вещь говорит об этом прямо. Нереализованный транспорт бросает NotImplementedError, а не делает молча не то. Нереализованная проба возвращает SKIPPED, а не OK.

Актуальный список «упомянуто в коде, но не реализовано» со ссылками на конкретные символы — docs/BACKLOG.md в репозитории. Это сознательная честность перед пользователем, а не забытый TODO-файл.
